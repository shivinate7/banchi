The wipe is off the table

Don't clear the inventory. The reason I gave you first was wrong; these three are not.

My original objection — that clearing would destroy $18k of hand-listed stock — was false. TCGplayer's Delete Inventory keeps prices and only zeroes quantities. But the audit found three things that break the plan for reasons I hadn't checked.

  • 01The wipe makes the re-push smaller, not bigger. _copies_out gates the sold-copy ceiling on read > 0, so an export reading zero everywhere falls back to the full pushed + staged of 1,181. Simulated: a full re-emit writes 300 copies today and 7 after a wipe. And nothing in the repo can reset pushed.
  • 02The post-wipe reconcile may be impossible. If the export comes back header-only, fetch_live refuses it outright as tcg_export_empty; if it comes back all-zeros, every ledger SKU lands in report.absent, which is not in settling, and the write loop never touches it. Either way the store cannot be told what happened.
  • 03The 43 records the reconcile creates fall into a hole. livecheck.py:188-192 drops any row where claim == 0 and quantity is 0 — into no bucket at all. Every D109 record has pushed = 0 by design, so after a clear their stale live is unsettleable and every later reconcile silently skips them.

Against a defect of 17 copies and $8.50, traceable to one known file, none of that risk buys anything. The negative-quantity CSV closes it in one upload.

Before anything touches TCGplayer

P1

Fix the merged-emit crash done · PR #216

pipeline/merge.py:170 does max(leg.match.live_cap for leg in legs). Since yesterday's D7 rewrite live_cap defaults to None, so this raises TypeError the moment one SKU appears in two runs — exactly the shape step 5 needs. My defect, introduced in PR #212. The two fields below it already use the right idiom.

# collect the real caps; no cap only when no leg names one, and the
# tightest bound wins rather than the loosest (a cap is a ceiling).
caps = [leg.match.live_cap for leg in legs if leg.match.live_cap is not None]
live_cap = min(caps) if caps else None
P2

Finish retiring the standing cap done · PR #216

pipeline/corpus.py:159 still reads live_cap: object = pricing.LIVE_QUANTITY_CAP, and to_payload writes it unconditionally, so a fresh store inherits the bound D7 retired. Change the default to None. Corpus.parse already routes through parse_live_cap correctly.

P3

Decide the cap for your store

Your inventory/prices.json holds "live_cap": 4. The code change does not reach a store that has the figure written down — _cap_for reads that key, and neither the CLI nor the ship bar can express "no cap" while it holds a number. With 403 copies unoffered, a cap of 4 is a large part of why. Remove the key, or set the send's cap explicitly in step 5.

03

Kill the 17 phantom copies no undo

Eight rows, negative Add to Quantity, uploaded once. TCGplayer's own documentation: "If you place a negative number in this field, it will remove that amount from your existing quantity… the minimum your quantity can be is 0." TCG Marketplace Price is required on every row — carry each SKU's current price through unchanged so nothing is repriced by accident.

This is a hand upload There is no in-app press for a quantity-bearing file. server/tcg_import.py:293-302 refuses any non-zero Add to Quantity by name (tcg_import_moves_quantity), and the push/publish buttons on #/pricing are markdown-scoped and price-only. Download it, upload once through Import to Staged, then Move to Live. A second upload doubles the correction — which is the exact mechanism that created this defect on 2026-08-31.

What this does not fix

  • The pushed ledger stays inflated. Store-wide pushed + staged is 1,181 against 922 verified live copies on managed SKUs. copies_out takes max(live, claim − sold), so it discards the verified reading wherever the unverified counter is larger — 31 SKUs / 88 copies today. The store-wide drawdown against a verified reading is the missing command behind all of this.
  • The claim == 0 hole stays open. Step 2 arms it on 43 records. It costs nothing while those SKUs stay in stock; the day one sells out, its stale live becomes unsettleable. Worth a fix in livecheck.py before it bites.
  • 71 on-hand cards carry no SKU and cannot be listed by any path until they are identified.
  • A SKU a card carries but with no listing record is reported under beyond this pipeline and then skipped by the write loop — D109's recording covers unknown rows only. Two such SKUs today, neither live.
  • Nothing records that an upload happened. pushed moves when the file is written; there is no history event for a live reconcile either. The receipt is the only trace, and it is terminal output.

If you still want the clear

It remains available and it is genuinely non-destructive — Delete Inventory on the Pricing tab, scoped by product line and set, gated behind typing your sales contact email, and prices survive. Two conditions have to hold before it is safe:

  • The restore cannot come from emit. It has to be a transform of the pre-clear export — Add to Quantity ← the shelf count for SKUs Banchi knows, ← Total Quantity for the 47 it does not. TCGplayer documents this rename for BinderPOS users. Build and check that file before clearing, so the window where nothing is for sale is minutes.
  • Confirm what a post-clear export looks like before relying on a reconcile to follow it. Header-only is refused outright; all-zeros writes nothing. Neither failure is visible until you are already cleared.
