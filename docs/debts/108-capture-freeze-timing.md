## DEBT108 — two capture timing checks go red on design-check shard 4

**What.** Two timing checks in `tests/capture-freeze.spec.ts` go red on `design-check (4)`, one by timing out and one by growth in blocked time per capture.

- **Tests and job.** `design-check (4)`, `capture-freeze.spec.ts`: test `50 captures while the dispenser deals` (run 2499, `Test timeout of 180000ms exceeded`), and test `hand-fed, captures 51 to 60 cost no more than captures 21 to 30` (run 2831, the median grew from 1052 ms to 1530 ms, against a limit of 1.4 times plus 30 ms). Two later first-attempt reds failed the second test the same way, against the same limit: run 3214 (id 41436198024), where the median grew from 936 ms to 1408 ms, and run 3258 (id 41623713142), where it grew from 938 ms to 1399 ms.
- **Measured.** 2 of the 100 most recent completed main check runs (window run numbers 2489 to 3148). Both were red on the first attempt. No retry is set. Both shards ran with 2 workers. After the window, runs 3214 and 3258 were red the same way. Both are nightly (schedule) runs, and both ratios sit near 1.5. The push runs on the same heads passed design-check. Each run sits near the limit, so early-window noise decides it. Run 3214's attempt 2 passed on the same head. A pass on a rerun does not clear the first red.
- **Cause.** Hand-fed test: cause read, and it is real growth per capture. In hand-fed mode the rail draws every tile (`railList` in `CaptureScreen.tsx`). The `DEALING_RAIL_TILES` cap applies only while dealing. Chrome's layout and style time per capture grows about 5 times from capture 5 to capture 60, 77 ms to 375 ms, while script time stays flat. Blocked time climbs about 8 to 9 ms per capture past capture 21. So the spec's comment that cost "saturates after ~20 captures" is false. Runner noise in the early window decides each run near the limit. Local runs: 9 of 9 passed, with ratios from 1.11 to 1.38. Timeout test (`50 captures while the dispenser deals`): cause unread. Its timed-out run measured a first-10 median of 4400 ms on a loaded shard. Not reproduced. Not read: the runner's load at the time of the timeout.
- **Owner.** shivinate7. **Fix by.** 2026-12-01 (D308, a deadline date is allowed).
- **Outcome at risk.** A capture screen that slows as cards arrive would freeze the operator's sitting. These checks guard that. A red from runner load alone wastes the guard.
- **Closes when.** Hand-fed test: the rail's cost is flat per capture (a fix lane is underway). Timeout test: its cause is written here. Then its limit is set from a measured spread, or the check reads load alongside the timing.
