## DEBT67 — capture photographs exist in one place

**Gap.** One copy exists, and only when the owner runs it. This is a one-time backup, by the owner's ruling: `make backup` copies `photos/`, `captures/` and a SQLite snapshot of `inventory/store.sqlite` to the iCloud Drive folder `Banchi backup`. The launchd agent (`make backup-agent`, `--agent` in `scripts/backup-daily.py`) is kept in the code and is not installed. The second copy is still missing. A photograph cannot be re-shot: the card is back in a box. Losing the disk and iCloud together leaves the realign (D36) nothing to bind to and the re-shoot (D26) nothing to compare against. On the owner's Mac, `photos/` holds about 7.9 GB and `inventory/` about 757 MB. Time Machine has no destination.

**A good copy is never replaced by a bad one**. `copy_tree` writes a file only when the destination has none. It skips a file whose size matches and whose mtime is within 2 seconds, decided by `stat` alone. A destination file with another size or mtime is left untouched and counted as `differs`: the run ends `failed` and the last-run line names the count. A re-shoot (D26) shows as differs. Accepting one is a manual act: delete its copy by hand, then run again. A file is copied under a `.tmp` name and renamed in (`move_in`), so a killed run leaves no half file that a later run would read as differs. `copy_tree` never deletes in the destination, so a sold card's photograph (D89) stays, and it never opens a destination file. One unreadable source file does not stop the run: the rest are copied and the run ends `failed` with the count. A missing iCloud Drive folder, a missing `photos/` tree or a linked worktree (without `BANCHI_BACKUP_DEST`) is a failed or refused run. `make status` shows the last run and marks one older than 36 hours as stale.

**The store snapshot is checked before it moves in.** `snapshot` makes SQLite's online backup in a local temp folder and runs `PRAGMA integrity_check` on it. Anything but `ok` raises before any `move_in`, so a damaged store replaces no copy in the destination and the run ends `failed`. SQLite's backup copies a damaged page without reading it, so this check is the only thing that stops it. Three copies of the snapshot sit in the destination. `inventory/store.sqlite` is replaced by every good run. `inventory/store-<YYYY-MM-DD>.sqlite` (`DATED_SNAPSHOT`) is written once per local day and never replaced: a second run the same day keeps the day's first copy. `inventory/store-weekly.sqlite` (`WEEKLY_SNAPSHOT`) is replaced only when its file is 7 days old or more.

**The shrink guard.** A store emptied by a bug or a bad restore must not replace the nightly and the weekly. A good run writes the `cards` and `boxes` row counts to a sidecar file beside the last-run line (`SIDECAR`). On a run when the weekly is due, a count more than half below the sidecar's (exactly half is fine) replaces neither snapshot and ends `failed`; the sidecar stays. The counts come from the sidecar and the local snapshot, never from the destination. To accept a real shrink, delete the sidecar. A folder under `photos/` that cannot be listed counts as one bad file. A linked worktree with `BANCHI_BACKUP_DEST` set writes neither the last-run line nor the sidecar, only a lock, because `~/.banchi` is shared (D43).

**`--verify`.** `python3 scripts/backup-daily.py --verify` (`make backup ARGS=--verify`) is read-only. It hashes (sha256) every file of `photos/` and `captures/` at the source against the destination and runs `PRAGMA integrity_check` on the newest dated snapshot. It prints matches, mismatches and missing, names each bad path, and exits non-zero on any mismatch, any missing file or a snapshot that is absent or not `ok`. It reads destination files on purpose, so it downloads any that iCloud evicted. It writes no last-run line and takes no lock.

**Limits.** First, the sidecar is rewritten after every good run. A store emptied between two runs becomes the new baseline on the next good run, so the weekly roll does not refuse it. The guard catches only a drop on the run right before the roll. The dated copies are the cover: an emptied store writes a new dated file and the earlier days stay. Second, a refused run's line in `make status` names no remedy for a shrink. It reads `failed snapshot failed: RuntimeError: the store shrank by more than half`, with the counts, and the way out is to delete `~/.banchi/backup-last-counts.json` (`SIDECAR`). Third, nothing deletes old dated copies. Each is a full copy of the store, so many days fill the folder until the owner removes some. Fourth, nothing checks that `render` in `scripts/status.py` still calls `backup()`. A lane that drops the call loses the `make status` line silently. Every status section shares this gap, and the home for a check is `check_status_sources` in `scripts/docs_audit/status_reach.py`. A backup job that fails to load prints "raised:" text in `make status`, and the exit stays 0. It is not a MISSING source.

**Second copy, on hold.** The Home Assistant box's 2 TB drive is the main suspect in that box's open data-corruption case (the home repo's `records/ha-green-freeze.md`). A drive health re-read decides it. If cleared: `rsync -a --partial` over the SSH add-on already running, to `/media/banchi-backup/`, which Home Assistant's own backups skip. A Mac launchd job, no `--delete`, and a weekly `rsync -c -n` check. The one-time ruling covers the iCloud copy only.

**Not a fix.** Do not move the live store or photographs onto a network share. `fcntl.flock` and `os.replace` do not hold over SMB, and the join hashes every photograph in a box, which is slow over wifi.
