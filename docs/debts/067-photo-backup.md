## DEBT67 — capture photographs exist in one place

**What.** One copy exists. A nightly job (`make backup`, installed by `make backup-agent`) copies `photos/`, `captures/` and a SQLite snapshot of `inventory/store.sqlite` to the iCloud Drive folder `Banchi backup`. The second copy is still missing. A photograph cannot be re-shot: the card is back in a box. Losing the disk and iCloud together leaves the realign (D36) nothing to bind to and the re-shoot (D26) nothing to compare against. On the owner's Mac, `photos/` holds about 7.9 GB and `inventory/` about 757 MB. Time Machine has no destination.

**What the first copy does.** It copies as files, skips a file whose size matches and whose mtime is within 2 seconds, and never deletes in the destination, so a sold card's photograph (D89) stays. It never reads the destination. One unreadable file does not stop the night: the rest are copied and the run ends `failed` with the count. A missing iCloud Drive folder, a missing `photos/` tree or a linked worktree (without `BANCHI_BACKUP_DEST`) is a failed or refused run. `make status` shows the last run and marks one older than 36 hours as stale.

**Two store snapshots.** The store is snapshotted first, in a local temp folder, and the finished file is moved in. The nightly snapshot (`inventory/store.sqlite`) is overwritten every night. The weekly snapshot (`inventory/store-weekly.sqlite`) is overwritten only when its file is 7 days old or more, from that night's snapshot, and never after a night whose snapshot failed. Both sit in the one iCloud folder: a bad night costs at most the nightly, and the weekly keeps the store as it was up to a week back.

**The shrink guard.** A store emptied by a bug or a bad restore must not overwrite both snapshots. A good run writes the `cards` and `boxes` row counts to a sidecar file beside the last-run line (`SIDECAR` in `scripts/backup-daily.py`). On a night the weekly is due, a count more than half below the sidecar's (exactly half is fine) replaces neither snapshot and ends `failed`; the sidecar stays, so the next night compares to the same good run. The counts come from the sidecar and the night's local snapshot, never from the destination. To accept a real shrink, delete the sidecar. A folder under `photos/` that cannot be listed counts as one bad file. A linked worktree with `BANCHI_BACKUP_DEST` set writes neither the last-run line nor the sidecar, only a lock, because `~/.banchi` is shared (D43).

**Two limits of the shrink guard.** First, the sidecar is rewritten after every good night. A store emptied in the middle of a week becomes the new baseline on the next good night, so the weekly roll does not refuse it. The guard catches only a drop on the night right before the roll. Second, a refused night's line in `make status` names no remedy. It reads `failed snapshot failed: RuntimeError: the store shrank by more than half`, with the counts. The way out is to delete `~/.banchi/backup-last-counts.json` (`SIDECAR` in `scripts/backup-daily.py`), which accepts a real shrink on the next night.

**Two limits of the status line.** First, nothing checks that `render` in `scripts/status.py` still calls `backup()`. A lane that drops the call loses the `make status` line silently. Every status section shares this gap, and the home for a check is `check_status_sources` in `scripts/docs_audit/status_reach.py`. Second, a backup job that fails to load prints "raised:" text in `make status`, and the exit stays 0. It is not a MISSING source.

**Second copy, on hold.** The Home Assistant box's 2 TB drive is the main suspect in that box's open data-corruption case (the home repo's `records/ha-green-freeze.md`). A drive health re-read on 2026-10-26 decides it. If cleared: `rsync -a --partial` over the SSH add-on already running, to `/media/banchi-backup/`, which Home Assistant's own backups skip. A nightly Mac launchd job, no `--delete`, and a weekly `rsync -c -n` check.

**Not a fix.** Do not move the live store or photographs onto a network share. `fcntl.flock` and `os.replace` do not hold over SMB, and the join hashes every photograph in a box, which is slow over wifi.
