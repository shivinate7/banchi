## D249 — Recognition by the complement, never by the expected pattern

**Reproduced 2026-09-20.** A real, correctly-slugged decision entry reached `origin/main` unclaimed. The branch that added it never touched `docs/decisions/ORDER.json`, by design. `settle_corpus` writes that manifest at CLAIM time, not before. `scripts/claim-ids.py --landed <rev>` and `make merge`'s own `landed_half` both read that commit. Both are the one backstop whose whole job is asking a REF what it carries. Both reported **"carries no unclaimed id — every heading in it is a number."** `make claim-stale` reported "nothing has gone stale" too. That was correct. Staleness asks a different question: does a NUMBER this branch adds collide with one `ref` has since taken? It never asks about an unclaimed slug at all. It was never blind to this. It was simply never the tool for it. `make docs-audit`'s `id claims` row caught it, unprompted, the moment it ran against that commit's checkout.

**The escape was not the heading's shape.** The owner's own diagnosis named a slug missing a "two-segment" shape. But `DECISION_HEADING`'s SLUG alternative matches a correctly-hyphenated multi-segment slug fine, case notwithstanding. The real mechanism was `corpus_text_at`. A REF has no working directory to `Path.glob` over. So the ref-reading half of the corpus trusted `ORDER.json`'s `order` list alone. It had no `git ls-tree` fallback for the extra files a working-tree read (`corpus_order`) finds by globbing. An entry-adding branch's own file is never in that manifest, on purpose, until the claim runs. So the one reader whose job is "what does this REF carry" could not see the file that mattered. The plain working-tree preview (`python3 scripts/claim-ids.py`, no `--landed`) found and correctly proposed claiming the same entry every time. `corpus_order`'s glob already covered the gap on a checkout with a working directory.

**A second, narrower escape sits in the heading grammar itself.** It would have mattered had the slug been irregular. `DECISION_HEADING`/`CODES_HEADING` require a NUMBER or a clean two-segment lowercase SLUG. They reject everything else outright, not by flagging it unclaimed, but by not matching at all. Three headings match neither alternative: `## D-SKU-number` (mixed case), `## D-sku--number` (a doubled hyphen), `## D0227` (a leading zero). Each is invisible to `pending_in`. Neither counted as claimed, nor reported as pending. Fixed alongside the ref-reading bug, by the complement. `unclaimed_from_pieces`/`unclaimed_from_flat` now ask only one thing. Does a heading open `D`/`C` followed at once by a digit or a hyphen? Does it then fail to be a clean, unpadded positive integer? If so, it is unclaimed, whatever shape the rest of it is in.

**A parallel bug sat in `docs-audit.py`'s `decision_files()`, one level upstream.** It filtered which files count as the corpus by a number-or-SLUG pattern. A separate loose/strict per-line check exists to report a malformed heading. That filter ran first, before the per-line check ever got to look. A malformed decision heading was excluded from the corpus before that check could run. `decision_files()` now includes any file opening `## D` followed by a digit or a hyphen, full stop. It lets the existing loose/strict check do the classifying. `docs-audit.py`'s CODES path already scanned unfiltered. It needed no change.

**One exception is kept on purpose, and scoped narrowly.** A one-segment heading in the legacy flat `docs/DECISIONS.md` format (`## D-pad`) is deliberately left as prose, not an id. `docs-audit`'s `id claims` row is what reports it as an unreachable heading. D160's own per-file naming convention means a real split-corpus entry cannot be created in that shape to begin with. The complement rule applies to the split corpus (one file per entry, standard since D160) and to the flat code-card ledger. The pre-split legacy fallback keeps its narrower, tested behavior unchanged.

**Scoped to the entry's own first heading, never any `##` line further down.** One file's entire content is the heading `## Deferred — argued, not gated: nothing here is blocked, and none of it starts without a decision entry`. That is a whole file's only heading, and it starts with the letter `D`. Scanning every `##` line in the concatenated corpus would have reported it as a second unclaimed decision beside itself. Reading only each file's own first line does not. It is excluded correctly because the character right after `D` is `e`, neither a digit nor a hyphen. The same complement that catches a malformed id also keeps an English word out of the id space. No separate carve-out is required.

**Same defect class as the `paths` row that ignored line numbers while reporting every reference resolving.** A guard that recognizes its subject only by the shape it expects sees nothing when the real world hands it an unexpected shape. It then reports the absence of a problem as the presence of a clean answer. The fix in both cases is the same. Ask what the subject actually is. A ref's own tree. A heading's own complement to "a clean number." Never whether it matches the pattern the guard was written against.

**Proved by `make claim-selftest`, extended with six arms.** The real escape: an unregistered entry file, read from a REF, checked both through `--landed` and through `drive_landed_half`. A mixed-case slug heading. A doubled-hyphen slug heading. A leading-zero, non-slug heading. A negative control for a `_`-prefixed file's own `## Deferred`-shaped heading. Positive controls for an ordinary numbered heading and an ordinary properly-slugged heading.
