## D148 — The wait is about the claim commit, and an answer it has not got is never a pass

**Found 2026-09-11, on two live merges the same evening D140 and D143 landed.** D140 sells one thing for the price of a CI run: *"main never takes a substitution no CI run has seen"*, printed by `scripts/merge-pr.py` in those words as it waits. It then called `gh pr checks <n>`, which asks about a PULL REQUEST rather than about a commit — and concluded from an EMPTY answer as readily as from a green one. Both halves are now the check runs attached to that commit, read until they are complete, non-empty, no smaller than the parent's, and unchanged across two consecutive reads.

**A guard that cannot tell "nothing is wrong" from "nothing is known yet" is the shape of all four defects in this one step, and there were four in one evening.** The claim half read the wrong TREE and the staleness check read the wrong TREE (both D143); the wait read the wrong COMMIT and a watcher read an EMPTY answer as a clean one (this entry). Each passed confidently while measuring something adjacent to the thing it named. **A fifth is worth looking for, and this sentence is here so somebody does.**

### Absence read as success is the worse half, so it goes first

**A commit GitHub has dispatched nothing for yet answers with an empty list, and "nothing is pending" read off an empty list is word-for-word the sentence "everything passed".** Pinning the question to the SHA does not fix that; it hands the same loop a subject that has no runs attached for the first seconds of its life, which is precisely the window a merge runs in.

**It was reproduced independently the same evening, by a session watching PR #277.** It called `gh pr checks 277` immediately after a push, got an EMPTY list back, counted zero pending, and reported SETTLED. Acted on, that merges a commit with **no checks attached at all** — strictly worse than the wrong-commit bug, which at least reads a real green tree.

**So a reading is conclusive only when it is all four things at once.** Non-empty. Complete. No smaller than the one the parent commit carried. And unchanged since the read before it. Anything else — an empty roster, a read that failed, a deadline — is `not known yet`, and every one of them is a REFUSAL rather than a fall-through. **`gh` being down is not evidence that a tree is green.**

**The two kinds of nothing are told apart where the reading is MADE, not downstream.** `Reading(False, (), err)` and `Reading(True, (), "")` both carry no runs and only the second is a fact about the commit. That distinction is invisible to a test that hands the loop a stub, which is why two arms drive `read_check_runs` itself and one drives the whole claim half against a `gh` that answers HTTP 422.

### The subject is the commit, and the pull request is not a near miss

**`gh pr checks <n>` answers out of the PREVIOUS head's runs until GitHub attaches runs to the new one.** They are complete and green — they are about a tree that merged fine — so the command exits 0 at once. **The faster the push-to-watch gap, the more reliably it reads the wrong commit**, and it has to see the old head GREEN to be silent, which is the whole reason nothing noticed: a previously-red head would have made it loud.

**Both merges were resolved by SHA rather than inferred.** PR #275: every job URL the merge printed belonged to run 34655700236, which is the PRE-CLAIM commit `0f166b8`'s; the claim commit `3ee3b00` had its own run, 34655942932, and that run was still `in_progress` when the merge fired. PR #277: read the instant the merge returned and pinned to claim commit `0f254802d`, four of seven checks were `in_progress` — all three `design-check` shards and `check`.

**Both trees later went green, and that is not the same as the guard working.** It would have been equally unkept had either been red. Two-for-two on claiming merges is the real rate.

**`repos/{owner}/{repo}/commits/<sha>/check-runs` is the question now.** Same repository — `{owner}` and `{repo}` are placeholders `gh` resolves from this checkout's remote, exactly as `gh pr checks` did — and only the subject moved. **The page size is in the query string and never in a `-f`**: `gh` switches the method to POST the moment a field is given, and that endpoint does not answer a POST, which cost this session a hung command before it cost anything else.

### The floor is the parent's count, because it is the only lower bound that is free

**A roster can be non-empty, complete and still half-attached.** One `success` out of the seven a tree will eventually carry satisfies "nothing is pending" perfectly. The parent commit — the pre-claim head — has had time to attach all of its runs, so its count is a number this check can have for one API call.

**It is a floor rather than an equality, and the direction is argued rather than assumed.** The diff a claim commit carries against main is a SUPERSET of its parent's, because the claim only adds; both gates this repo runs on that diff widen under a superset — `browser-scope` (D141) goes skip to run, and `already-passed` (D136) cannot make a changed tree skip. Measured: #275's parent carried 6 runs and its claim commit 8, because a skipped `design-check` became three shards; #277's parent carried 8 and its claim commit 8.

**A floor that is never met RUNS OUT and refuses, naming the shortfall.** That is the right failure direction for a gate whose other option is a false green, and it is loud rather than silent — which is the test D140 applies to the collision it deliberately leaves open.

### Where it lives, and where it deliberately does not

**In `scripts/merge-pr.py`, which already owns every `gh` call on this path.** D140 spends a paragraph refusing to grow a `gh` dependency in `scripts/claim-ids.py`, and that refusal is untouched: the claimer still reads local refs and nothing else. **This is D143's finding applied one function along** — the precondition belongs where the pointing happens, and only the merger knows which commit it just pushed.

**Twenty-five arms and six mutants, in `scripts/claim-selftest.py` beside D143's own.** Ten drive `wait_for_checks` with a scripted reader and a clock that moves only when the code sleeps, so the forty-five-minute deadline is the one that ships and the arm is instant. The rest drive the REAL claim half — real claimer, real commit, real push to a throwaway origin — with a fake `gh` on PATH that answers `gh pr checks` **green and instantly**, the way the real one does. **A wait that asks the pull request therefore PASSES against that fake**, which is what makes restoring it turn four arms red rather than merely making them slower. Restoring empty-as-clean turns four red; dropping the settle, seven; dropping the floor, one; collapsing an unreadable answer into an empty one, one.

### Amended the same day: there are two guards now, at two layers, and neither retires the other

**GitHub's required status checks were turned on for `check` and `revert-guard` on 2026-09-12, hours after this was written, and they close the same race server-side.** `enforce_admins` is true and `strict` is false, so the gate binds everyone and does not demand the branch be current. It proved itself on the merge that landed immediately before this one: that pull request's merge was refused as BLOCKED because its claim commit's `check` was still in progress — the case that bit #275, #277 and #278.

**It closes more of this entry than the sentence above admits, and that is worth saying plainly.** For those two contexts the server gate refuses a merge both while they are RUNNING and while they are ABSENT, because a required context that is not present is not satisfied. So the wrong-commit half and the absence half are both covered — **for `check` and `revert-guard` and for nothing else.**

**What it does not cover is the expensive half.** `design-check` is not a required context, so a merge is free to proceed while three browser shards are still running or already red. That is the half that takes 8.4 minutes and the half D136 and D141 spend their gates on, and the wrapper's wait is the only thing that sees it today.

**Requiring the shards is not one settings change away, and the reason is a fifth instance of this entry's own sentence.** The matrix reports `design-check (1)`, `(2)`, `(3)` when it runs and a single `design-check` when `browser-scope` skips it, so the shard names are not a fixed set — measured across `0f166b8` and `3ee3b00`. There IS a fixed name in both shapes, `design-check-passed`, and it looks like the aggregator to require. **It is not safe to require as written**: it is `needs: design-check` under the implicit `success()`, so a FAILED shard makes it `skipped` rather than `failed`, and a skipped check run is not a failing one. A guard that cannot tell "the shards passed" from "the shards never reported" is the same defect at the CI layer, and requiring that context would install it. **This is recorded as a finding, not a change** — nothing here touches the workflow or the protection settings. **And it is not queued work**: the session that turned the required contexts on reports the owner ruling separately against requiring the browser suite at all, on the ground that a flaky gate teaches a reader to reach for `--admin`. That rate is real and open — 1 in 13 completed `design-check` jobs since D128 merged, whose only known mechanism is "the suite around it" (DEBT8 — not §11, the capture-server section. Measured 2026-09-12: of sixteen citations of §11 in the tree, seven meant §8 and nine were right, so a blanket substitution would have broken nine to fix seven. (This sentence said nine and two until the repair landed: that count came from a pattern requiring nothing between the filename and the reference, which cannot see a site spelling it DEBT11 with backticks. `D149` carries the population and the three spellings.) Repaired separately the same night; the direction was a propagated copy rather than a renumber). So the aggregator's skipped-for-failed reading is a trap to know about rather than a defect to fix, and a session proposing the fix should read this paragraph first.

**The other difference is register, and this repo already ruled on it.** The server gate refuses with a merge-state error; the wrapper refuses with a sentence naming which check is still running and for how long. `make design-check` names the tree holding the lock and exits 75 rather than failing opaquely (D122), and this is that same call one command along. **A backstop that only ever fires as an error is a backstop; it is not a wait.**

### What it does not decide

**Not that a commit status is the same thing as a check run.** This reads `/check-runs`, which is GitHub Actions and the only kind this repository has — and the required-contexts gate above reads the same shapes, so neither layer sees a status the other misses. An external service reporting through the statuses API would be invisible to it, and the floor would not notice either, since the parent's count comes from the same endpoint. **Not the deadline's value**: forty-five minutes is a guess sized against a suite measured at 8.4 minutes (D136) and it has never been reached. **And not whether a green claim commit means a green merge** — the merge commit is a different tree and nothing here waits on it, which is the same thing D140 said and is not reopened.

### Amended 2026-09-19: wait on required checks only

**The owner's word, quoted: "Wait on required checks only."** Every merge paid for the three `design-check` shards even though branch protection has never required them. Measured before this change: `check` finishes in ~3.7 minutes, `design-check` in ~8.7. The wait above waited for both. That is where 8-9 of every merge's minutes went.

**What is let through, named plainly.** `wait_for_checks` now takes a SUBJECT to wait for completion of: `main`'s required status-check contexts. These are read from GitHub at the moment of the wait (`required_contexts`, `repos/{owner}/{repo}/branches/main/protection/required_status_checks`), never a typed list. A typed roster goes stale the instant protection changes, silently — the shape of defect this whole entry is about. Once the required contexts are complete, green, non-empty, no fewer than the parent's own count of required contexts, and unchanged across two reads, the wait returns green. It does this **even while a non-required run — `design-check` foremost — is still running.** A merge can now go out while the browser matrix has not finished. That is on purpose, for the first time since D140.

**What is NOT let through.** A run that is already visible and RED still refuses the merge, required or not. The `failed` check reads the whole roster, never only the required slice. Narrowing what is WAITED FOR is not narrowing what is WATCHED FOR. A known red is not something to merge past. It is only something that need not be waited for, if it has not reported yet.

**A read failure narrows nothing.** An unreadable protection endpoint returns `None` from `required_contexts`. So does a `contexts` answer that comes back empty, or with nothing readable as a name. Either way the wait falls back to the old, untouched behaviour: wait for every check run. "Required" cannot be told apart from "everything" off either answer. D148's own non-vacuity rule — an empty roster is never a pass — applies to this roster too.

**At the moment a required-only wait goes green, the merge prints two things.** First, which non-required runs are still going, by name. Second, this fixed sentence: *"the browser matrix is not required and was not waited for; a red there lands on main's own run and is fixed forward (owner's ruling 2026-09-19)."* That push-triggered run is D136's own mechanism: the workflow runs the full matrix on `main` whenever no pass record exists for the tree. A `design-check` red that slipped through this narrower wait is caught there, on `main`'s own run, not silently.

**Thirteen of `scripts/claim-selftest.py`'s arms cover this directly, and every one is mutation-tested.** Required green with a non-required run in progress merges, and names it. Required green with a non-required run RED still refuses. A required context not yet attached holds the wait, exactly as full absence did before. The floor counts required contexts only, never the roster's total. An unreadable protection endpoint and an empty (or unreadable) `contexts` answer both fail closed to the old wait-for-everything behaviour.

**What this does not decide, unchanged from the paragraph above it.** Not that a differently-shaped required context (`design-check-passed`'s skip-vs-fail, named in the finding above) is now safe to require. Nothing in the workflow or the protection settings changed here — only what THIS wait waits for, once GitHub is asked which contexts protection already names. If protection ever names a browser-matrix context directly, this wait includes it without a further change, because the roster is read, never assumed.
