## D-readings-table — The market reading is a table, and the walk that fills it is a press

**A LIVE RECOMPUTATION BECAME A CACHE, AND THE ARBITRATION IT RAN DID NOT CHANGE.** `server/pipeline_routes.py:_readings()` used to walk every run's `runs/<n>/pricing.json` and the newest file under `inventory/.live` on every single `GET /pipeline/value`, comparing the two sources on a clock and returning `sku -> the newest market price this machine has read for it`. That walk is unchanged in substance — `pipeline/readings.py:collect()` runs the identical newest-wins comparison, over the identical two sources, and nothing about WHICH reading wins moved. What moved is WHEN: from every request, to one explicit press, `pkmnscan readings adopt --write`, which folds the result into a new `readings` table in `inventory/store.sqlite` (D88). `_readings()` is now a plain `SELECT` against it.

**THIS IS THE LOWEST-STAKES PR THE `unbox-plan.md` BUILD ORDER NAMED, AND IT STAYS THAT WAY.** It fixes no bug, corrects no wrong price, and changes no arbitration rule. What it buys is architectural: a request that used to re-parse every `pricing.json` in `runs/` and one live-export CSV now reads two small tables. On a store with a handful of runs this is not yet a measured cost — nobody has reported `#/pricing`'s value screen as slow — so this entry records a simplification made ahead of a complaint rather than in response to one, and says so rather than inventing urgency it does not have.

### Two tables, because one answer has two shapes

`readings` is `sku -> Reading` (`market`, `at`, `source`, `kind`, `name`, `set_name`, `condition`), one row per SKU — the exact mapping `_readings()` always returned. `readings_sources` is the accounting beside it: which files answered, and how many SKUs EACH ONE offered **before** arbitration.

That second table earns its place rather than being convenience. A run table that priced 100 SKUs and lost 20 of them to a newer live export leaves only 80 rows in `readings` carrying its name — the winners. The old function's `sources` list reported the full 100, because it counted every row a file offered on its way past, not the rows that survived to be the final answer. A caller asking "is this a thin STORE or a thin FETCH" needs the pre-arbitration number, and it is not recoverable from `readings` alone once two sources have collided on a SKU. So `readings_sources` is a second table, filled by the same `readings adopt` press, keyed by `kind:name` rather than by `name` alone (a run directory and a live export filename do not collide in practice, but nothing about this table's contract should depend on that being true forever).

### Why `readings adopt` is a manual press, and why that is a real question here

`pkmnscan prices adopt` (D86) previews by default and is a deliberate press because folding a run's `decisions.json` into the shared pricing corpus is a **real decision**: newest-wins can silently replace an operator's deliberate price hold with a figure nobody meant to compare it to, and three of the eight SKUs on the owner's own store were exactly that collision. A migration nobody watched is how that goes quiet a second time.

`readings adopt` previews by default too, on the same shape, but the reason underneath it is different and weaker. **There is no operator judgement inside this walk at all.** `readings` holds no hold, no override, no hand-typed answer — it is what the market said, arbitrated on nothing but which file is newer. Running the same walk twice over the same files produces the same answer both times, and a wrong answer here is never a silently-overridden human decision; at worst it is a stale market price, which is exactly the failure mode the live recomputation ALSO had between two runs' worth of activity (nothing kept the value screen fresh to the second before this either — it was fresh to the last completed join or live fetch, never faster than the operator's own last action). So this entry answers the question the PR's own task description asked to have answered explicitly:

**The table does not self-maintain, and `readings adopt` is a manual press rather than something a join or a live fetch triggers automatically.** The alternative — writing into `readings` from inside `do_pipeline_pricing`'s join and from inside `do_live_export`'s fetch — was considered and set aside for now, for a reason that is really about scope rather than about correctness: it would mean two more write paths reaching into the store's transaction from code that today writes only files, and the PR that does that safely is a bigger and different PR than "recompute-every-call becomes read-once-write-many." A manual press is also consistent with the one thing this feature is not: nothing downstream has ever needed sub-second freshness on a market reading, and `#/pricing`'s value screen already tolerates staleness up to "whenever the operator last joined or fetched." **If a session finds that gap costing something real — a stale reading actually misleading someone at the rig — the fix is to make `join` and `do_live_export` call `readings adopt`'s writer at the end of their own transactions, not to relitigate this entry.** That is a small, well-scoped follow-up and is named here so the next session does not have to re-derive it.

### The table is a cache, and a press replaces it wholesale

`Readings.replace()` clears every row in both tables and writes exactly the fresh set `collect()` just computed. This is deliberate and is the one place this entry is emphatic: **a SKU whose only source has since been retired — a run directory deleted, a live export superseded and removed by hand — must disappear from the table exactly as it would have dropped out of the old live walk on its very next request.** An incremental merge that only ever added rows would let `readings` accumulate stale answers the live version never could, which is the one way this change could make the store WORSE than the thing it replaces rather than merely different. `store/rows.py:Rows`'s diff is baseline-based, so a full clear-then-reinsert writes only the SKUs that actually changed — a SKU whose reading is unchanged between two adopts costs nothing in the transaction, and only new, changed or genuinely-dropped rows touch disk.

### What was proved, and how

`scripts/readings-selftest.py` runs `pipeline/readings.py:collect()` against an independent, separately-written reimplementation of the same walk (`golden()`, not sharing a line of code with `collect()`) over a throwaway store, across: an empty store; a store with only run tables; a store with only a live export; a run and a live export disagreeing on one SKU, both directions of which one is newer; the newest-by-name live export carrying an unparseable filename (it must lose to everything and must not fall back to an older, readable file); `readings adopt --write` followed by the exact `SELECT` `_readings()` now performs, asserted equal to what was just adopted; re-running `adopt --write` twice unchanged (idempotent, no duplicate rows); a new run landing between two adopts (picked up on the next press); and a run directory being deleted between two adopts (its SKU disappears from the table). Thirty-one assertions, all passing. `make harness` is unaffected — no test in that suite exercised `_readings()` directly before this, and the harness fixtures carry no `readings` expectations of their own.

### What this does not touch

The two-source arbitration rule itself — newest wins by clock, never by a fixed precedence — is D86's own reasoning applied one register over from the pricing corpus to the market reading, and it is unchanged in every particular. `pipeline/pricing.py`, `pipeline/corpus.py` and `inventory/prices.json` are untouched; this is about where a market OBSERVATION is cached, never about what an operator DECIDED to ask for a card.
