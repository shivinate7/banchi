## D91 — The order fetch counts by status first

**The fetch walks the search pages whole and counts by the status string TCGplayer gave each order.** Only the statuses the operator ticks are detailed.

- **The status is the operator's, never the code's.** A string this module decided meant "still needs picking" would be a guess, and a guess that drops an order is an envelope that never ships. `POST /orders/fetch {preview: true}` walks the summaries (`order_transport.summaries`, one request per 25 orders, no detail call) and answers counts by status, verbatim, with how many of each the ledger already holds. `{statuses: [...]}` details only the ticked ones, compared verbatim after a strip, never folded, mapped or made a constant. `{all_statuses: true}` is the explicit "every one". A call naming neither, or both, refuses `statuses_required`. The ordinary press is all statuses and skip-known, with the picker as the secondary "Only these statuses…" control (D193). The tick is remembered on the device (`banchi.orders.fetch-filter`).
- **The cap is on the detail calls, not on orders in the window.** Pages are cheap and details are the cost. The bridge extension holds itself to 120 requests a minute, which is that client's own limit and not a measurement of TCGplayer. A guard sized to the wrong quantity (100 orders against 370 in the window) made the route unusable on the one account it serves, and no test held a fixture that large. Past the cap the rest is counted and answered as `remaining`, never silently left, and the next press picks it up. `skip_known` hands the transport `{number: status}` from `_known_orders`, so an order already detailed at its status is not detailed twice, and an order whose status moved is detailed again.
- **The transport does not sleep.** A route pausing through 370 details would block one HTTP request for minutes. Two presses inside a minute can pass the budget, and there is no cooldown.
- **The status strings are TCGplayer's.** The filter and the delta compare the summary's `orderStatus` with the ledger's status, which came from the detail. If the two spell one state differently, `skip_known` re-details that order every press, and the preview shows the doubled string. The `Custom` date range is not captured, so the window is three months or two years.

Reopen for a status spelled two ways, a captured `Custom` range, or orders arriving faster than a person presses. An unattended fetch is its own entry, since a cookie can expire under the supervisor with nobody watching.
