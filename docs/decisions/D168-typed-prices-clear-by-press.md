## D168 — Typed prices clear by press, never expiry

**A typed pricing answer stands until the operator clears it.** `#/pricing` has one control that clears many at once, scoped, counted in its own label and reversible. There is no TTL, auto-stale or expiry anywhere: the owner refused an expiry rule and asked for a mass-clear button. `older_than_days` is an argument to one call, spent by one press, and nothing runs on a clock. 269 of the owner's 407 typed prices were five days old and still pre-filling their fields.

- **It may clear exactly what `stamp_answers` dates.** `pipeline/corpus.py:clearable` uses `channel == "price" and not is_hold`. An answer that earned a date is a typed price, and otherwise it is a judgment or the absence of an answer. `check_pricing_clear` asserts both against each other. It never touches:
  - *A hold.* Clearing one puts the card back into the next `emit`, a money consequence in the costly direction. No control reaches holds, and the sheet says the figure.
  - *A `channel != "price"` answer.* `cli/cmd_join.py` seeds `Answer(value=None, channel="unknown")` for every card the catalog could not price, and `pipeline/decisions.py:blocking` reads it to decide whether `emit` refuses.
  - *An undated answer.* An age window cannot place it, so it skips it and names the count. `Any age` takes it like any typed price. A `null` age is reported as `null` and never `0`.
- **The blast radius is a control.** `inventory/prices.json` is one file for the whole store (D86), so the sheet asks the scope first: `On this worklist · N` (the SKUs the screen loaded, named as the header names them) or `Everywhere · M` (it says every run at once). The figure is in the button's own label (`Clear 269 typed prices everywhere`). The scope is the worklist and not the visible rows, since lens chips and the cut-off move the visible set. A destructive press must not depend on a chip. The sheet opens in its safest state each time (worklist, `Any age`) and never remembers the last press. There is no default window, which would be the refused expiry.
- **Every window draws its own count** (D103): a window can be empty for a reason about the store's age. The two-line cells are not the kit's `Segmented`, which has no shape for a word plus a figure.
- **Two routes carry D86's revision guard.** `POST /pricing/clear` removes and hands back what it removed. `POST /pricing/restore` puts it back. One file may not have two unguarded writers (D105), and an absent revision lands as the PUT does. A clear is its own route and not a `PUT` of nulls. Otherwise the client would decide which keys, which is `corpus.clearable` written again in TypeScript against money. The client's SKU list is a scope and never a predicate: the route re-derives membership on every call, so a stale list removes fewer answers and never a different set. `check_pricing_clear` presses a hold and an `unknown` seed and requires nothing cleared. The counts the label needs ride `GET /pricing`'s envelope beside `revision`, never inside `corpus`, which round-trips unknown keys and would store them.
- **The way back is the answers with their dates.** `cleared` carries each answer's `value`, `at` and `from_run` verbatim. `restore` writes `at` verbatim without stamping, or `priced_recently` would refuse every restored SKU (D103's ratchet inverted). It writes only a SKU the corpus no longer answers, so an undo cannot overwrite a price typed since. Skipped ones come back in `skipped` and the toast names them.
- **The screen refuses the press while it has unsaved work,** because autosave of the whole document would silently undo the clear. It does not reload afterwards (skeletons would flash across the list, D118). It holds the server-confirmed document minus the cleared keys, with `book` and `savedBook` on one object so `dirty` stays false. It re-reads `clearable` so a reopened sheet does not count gone answers. It does not adopt answers from that read. Never assign a ref inside a state updater: StrictMode runs the updater twice, and the first build PUT the stale document over the file that holds money.
- **Not this control.** No hold is cleared by any control here. Nothing is scoped to a run's own answers (a price is a fact about a SKU, D7, D86). No file is written and nothing at TCGplayer moves, and a cleared row goes out at the standing rule when `emit` runs. `pipeline/reprice.py:_parse_stamp` delegates to `pipeline/corpus.py:parse_stamp`, so `priced_recently` and a mass-clear cannot disagree about which answers are old.

Reopen if an operator clears the same window every week (the expiry was right), if holds accumulate the way typed prices did, or if every press is `Everywhere`.
