# D73 — Screens re-read after every write, whatever its outcome, and when the operator returns

Screens re-read after every write, whatever its outcome, and again when the operator returns.

Kind: process
Home: app/src/afterWrite.ts

**Two questions look alike.** `X-Banchi-Boot` (`BOOT_ID`, `noteBoot`, `onServerBoot`) answers whether the code changed. It rides traffic that exists because a restart happens while the operator works. Nothing can answer whether the data changed. A screen goes stale because nobody touches it, so it has no traffic to ride. A data-generation header is what the boot header's own design says that nothing can supply.

- **The reading is unsafe, not the write.** Under D58 a stale number names a different card. The operator counts to it in a drawer and pulls the wrong one. The stored index never moves, so a stale screen's write still lands on the record it names. The phone's `UndoTarget` label goes stale too.
- **Re-read after every write, whatever its outcome, and when the operator returns. Never re-render while they are on the screen.** Every write starts the screen's re-reads: an answer, a refusal, a 5xx or a network error. A refusal still says the screen was behind. A failed write may still have committed, so the screen cannot know it is unchanged. `app/src/afterWrite.ts` is the one home: `afterWrite` runs a write and starts the re-reads in a `finally`, without awaiting them, `rereadNow` starts them directly, and `useRereadOnWrite` registers a screen's reads. The re-reads never block the next press and never refetch a list that reorders (D313). `app/src/Orders.tsx` and `app/src/Fulfillment.tsx` are on the helper. Fulfillment's writes (a sale, an undo) run through `afterWrite`, and its `reread` counter is registered with `useRereadOnWrite`. Other screens keep their own re-reads until a follow-on lane moves them onto it. That move is the open scope: Inventory in its own PR, then the rest. Fulfillment is also the idiom for return: leaving a card and "Try again" still call `reread` directly. It never re-reads on a timer that reorders a list under a thumb (D28). Every route change unmounts the view, so arrival is a full re-read. Polls use `usePoll` (D207). `#/review` never re-renders mid-session. `#/inventory` is the urgent case, because a capture from the phone changes the labels the walk draws. A notice with a control is refused (`docs/DESIGN.md` bans acknowledgments).
- **No live connection.** Every verb funnels through `_dispatch`, which counts requests in flight. So a held stream turns each watched Python save into a 35-second stall, a 40-second grace and a SIGKILL. `REQUEST_SLOTS = 4` makes one stream a quarter of the server's capacity. `app/tests/cursor.spec.ts` waits for `networkidle` inside a `.catch`. So an open stream keeps the suite green and about three and a half minutes slower. A WebSocket adds a dependency to the one process that may never need `make venv`.
- **A signal would be a monotonic counter in `store/session.Store`,** the funnel every mutation passes through, coalesced. The feeder fires at a 623 ms median, so per-generation events become furniture. A random id like `BOOT_ID` cannot be compared or coalesced. It is banked, not built.
- **`markSold` and `undoSale` take `(box, index)` and carry no aim check.** Only `removeCardInPlace` and the order pull are `capture_id`-aimed. The wire does not refuse a stale press.

Reopen for a second pair of hands. A real Fulfiller and the owner writing at once is too fast for return-to-screen.
