## D207 — The foot learns from every request, and five timers become one hook

**The sidebar's server dot could lie for up to fifteen seconds, and the fix is not in the dot.** `App.tsx:useServerPresence` used to learn the capture server was gone only from its own `GET /status` poll — on mount, every 15s, and on window focus. Every OTHER request the app makes can fail without ever touching that state, so the foot went on drawing `Server online · 2,535 cards` while a press on `#/runs` was failing outright. `server.ts:request()` is the one seam every client call in this module passes through — the same seam `noteBoot` already uses to fan a boot-id change out to `onServerBoot` listeners — so reachability is observed there instead of re-derived per screen. `noteReachable(ok)` fires on both the success and the failure path of every fetch, and only when the state actually changes; `onServerReachable` lets the shell subscribe the way it already subscribed to a restart. A failing fetch that the server still answers `/status` for (an unfamiliar origin refused at the CORS preflight) reads as reachable rather than offline, because the server genuinely is up — that distinction is `origin_blocked` and predates this entry.

**Five hand-rolled timers stood where one primitive belongs, and `usePoll.ts` is that primitive.** `RunPanel.tsx` polled the run list and, separately, an open run's own detail; `BoxRuns.tsx` copied the run list's 4s/20s pair *by comment* rather than by any shared code; `SubmissionClaims.tsx` polled at 8s while a claim was live; `App.tsx`'s own `/status` poll ran at 15s and on focus. None of the five paused while its tab was hidden, none backed off when the server stopped answering, and none of them were counted against how many requests the capture server can actually run at once — `server/capture_server.py:REQUEST_SLOTS` bounds that at 4, and §11 measured that less concurrency is strictly better on this rig, the opposite of the instinct that would add a sixth timer on top of the other four. This was CLAUDE.md's own test for a bandaid: the primitive was unfactored, not missing — three of the five already wanted a live/idle cadence pair, and the migration is the proof rather than a separate claim: all five callers move onto `usePoll` in this change, and their existing specs staying green (`run-panel.spec.ts`'s 71 cases, `inventory.spec.ts`'s 112, `orders.spec.ts` and `capture-claims.spec.ts`'s 74, `nav.spec.ts` and `brand.spec.ts`'s 33) is what verifies it — a new spec asserting the hook in isolation would prove only that the hook works, not that the five screens still do.

**What the hook owns that no single caller had before**: a pause while `document.hidden`, with an immediate tick the moment the tab is looked at again; a backoff that lengthens the idle cadence on a run of consecutive failures rather than hammering a server that just went quiet; and one module-level counter, shared by every `usePoll` in the app, that never lets more than `REQUEST_SLOTS` (4) requests be in flight against the capture server at once — the accounting §11 asked for and no poller had.

### Deferred, not refused: the Orders live subscriber

A sixth consumer was considered — the order screen picking up an arrival with no Fetch press, the natural next thing to build on this hook. **It is deferred, on measurement, not built.**

There is no cheap "anything new?" call: `server/order_transport.py:search_body` hardcodes `sortBy` ascending on status then date with no direction parameter, so a single page cannot surface the newest order, and `totalOrders` moves on an arrival but sits still through a status change and cancels out on a simultaneous add and remove — nothing in the shape of the answer says "something changed" cheaply enough to poll for. A poll would also hold one of four `REQUEST_SLOTS` for the whole outbound round trip, up to `TIMEOUT_S = 30` — a quarter of the server's execution capacity per tick, against the exact measurement in §11 that less concurrency is better here, not more. And the transport has no throttle and says so itself: `fetch_open_orders`'s docstring reads *"IT NEVER SLEEPS… Two presses inside one minute can pass the budget and this module does not stop them; D91 names that cost."* A poller is exactly that shape repeated on a timer, so a live link would have to build the throttle D91 already declined to build.

**The outcome test that decided it**: the owner's own open-order count went from 697 to 14 the day the ledger's buyer-per-drawer walk landed, and Fetch is one click. A poller that costs a quarter of the server's capacity per tick to detect an arrival, against a transport with no cheap delta and no throttle, does not make an order ship any sooner than the press already does.

Reopen this when either measured fact changes: the owner presses Fetch by hand for a week on the new screen and it visibly bothers them, or `order_transport.py` gains a `since` / newest-first parameter that makes a cheap delta possible. Until then `usePoll` is built to take a sixth caller — nothing about it is Orders-specific — and this paragraph is where that session should start.
