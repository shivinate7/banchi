## D174 — A paid press claims its cards atomically

**A press claims the position keys it is about to pay to read, in the `submissions` table, and a second press is refused on intersection.** The claim is written by the command that spends, in the same `Store.write()` that recomputes what is being bought. The send list is decided about a minute before the claim (hashing 678 photographs), so two presses can both finish deciding and both believe they are first. A box number is not the guard.

- **The box number is wrong in both directions.** `server/pipeline_routes.py:_busy_run(box)` refuses a second identify while a live run reads the same box. It is too wide: two live runs over disjoint selections in one drawer are refused, and nothing would be double-billed. It is too narrow, which is the half that costs money: `_run_box` answers `None` for a run whose captures span more than one box (`cmd_identify:_scope_for` returns no scope for two boxes), so a box press and that run do not see each other. Widening it to store-wide still compares `None` with `3`. The vocabulary is the problem. The identification cache cannot stand in, since an entry is written after collection, so two racing presses both consult an empty cache and both pay.
- **A key is `box/index` (`identify/sidecar.py:key`),** the string the cache, queues and join use. Disjoint selections do not intersect, and a press spanning drawers intersects a box press on the cards they share. `store/submissions.py:conflict_sentence` composes the refusal once, naming the receipt and the overlapping cards. It truncates the cards and never the count, since two cards is a double-click and four hundred is a different mistake.
- **What is claimed is the send list and never the selection.** On the store 2,321 of 2,535 cards are cache hits, so a press over everything claims about 214 keys. A table claiming the selection would lock the store on the first press and get switched off. A press with an empty send list writes no row.
- **The check and the write are one transaction.** `claim_or_refuse` recomputes the miss set from the cache it is handed, intersects with the live claims read in that transaction, and writes the row before the lock is released (D88: `BEGIN IMMEDIATE` under the flock). The caller passes digests it already computed, since digests cannot move under a press and hashing thousands of files under the lock is wrong. Where the recompute narrows the send list, the dropped cards adopt the answer the store now owns (`cli/cmd_identify.py:_adopt_cached`). `force` is the deliberate re-read (every `--reidentify-stale` target is a cache hit by construction). `resuming` releases only the named run's claims, so it is not a back door.
- **A row does not self-heal.** A run killed after it submitted has a batch in flight at Anthropic, kept for 29 days, so a guard that dropped the row on finding the pid gone would hand back a green button over an invoice already rung up. `holder_alive` is reported and never acted on: the screen says wait for a live holder and offers a release for a dead one. Liveness is the pid plus the `ps -o lstart=` string recorded at claim time and compared exactly on read (both values come from one source and format). The console app's session records are not consulted, since the holder is a `pkmnscan identify` child. Unreadable reads live: a false live over-refuses, and a false dead is the double invoice.
- **One release is not the banking commit.** `cli/cmd_identify.py:_give_back_unspent` gives a claim back only when `run_dir.batch_ids` is empty. `identify/batch.py` records each id through `on_submit` as it submits, so no id is proof nothing is in flight. It is not a `finally`, since a caught exception cannot tell an unspent press from a half-spent one. It exists for the ordinary self-inflicted failure, a bad API key on a fresh checkout.
- **The way out is the whole chain.** `POST /pipeline/submissions/<receipt>/release`, `releaseSubmission` in `app/src/server.ts`, and `app/src/SubmissionClaims.tsx` on `#/runs`, where the refusal already sends the operator. The free count (`GET /pipeline/submissions`) comes first. A live holder is not offered a release at all (absent, not disabled), since releasing re-opens the cards to the double invoice. The panel draws nothing when nothing is claimed, so it is a panel and not a route.
- **Two refusals, and only one is the guard.** `claim_or_refuse` is binding and atomic, and it covers every press path (screen, terminal, agent). `_claim_conflicts` is a courtesy that intersects selection keys before any child starts and answers the ordinary double-click with a sentence. It can be beaten by a press between the read and the spawn, and it can over-refuse a cache-hit card that is another press's live miss. `_busy_run` stays, since a guard is removed only after its replacement has been exercised.
- **The work is counted, not the outcome.** A claim table that claimed nothing lets every press through while every "the press succeeded" assertion passes. `submissions.counted` publishes rows live, cards locked and dead holders, and the panel draws the card count beside the row count. The suite refuses to pass over nothing: a zero total exits non-zero, a case with no checks fails, and the attempted count is compared against `CASES`. `case_claims_the_send_list_only` is the only case that tells the send list from the selection.
- **`make submission-selftest` is in `make check` and never in the git hook** (D18). It runs against a throwaway store with `PKMNSCAN_HOME` repointed. It reproduces the bug first: two real processes in the check-then-claim order both buy the card, and through `claim_or_refuse` exactly one wins, six of six. The barrier is a barrier and not a sleep (D136). Sixteen mutation arms are killed. One case shares its card with the lowest-numbered box only, so a guard narrowed to the first drawer passed, and a two-drawers-along case was added. A `Store` built before a second `fresh_store()` stays bound to the first store's directory and made two assertions pass for the wrong reason.

Not proved: no claim has been written by a press that went on to spend (the self-test races `claim_or_refuse` and not the Batch API), so the release-on-bank path has never run. The release control has been pressed only against a seeded claim whose holder was killed with `-9`.
