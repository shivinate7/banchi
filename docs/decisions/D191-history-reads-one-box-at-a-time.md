## D191 — History reads one box at a time

**The problem, measured on a `.backup` copy of the real store, scaled 20x.** `Store.history()` runs `SELECT id, payload FROM events ORDER BY id`, unconditionally, on every call. Measured: 16.5 ms at 12,654 events, and 345 ms at 20x (253,080 events, 20.9x). It runs inside the store's write lock, on the hottest reversal paths in the product. Those are a mark-sold press, a retirement, a review answer, and a stand-down reversal. Every one of their callers runs it unconditionally, including a plain sale or retirement (`undo=False`). Both routes' response bodies carry `"restores_to": None if undo else previous`. That tells the caller whether an undo would be offered, before they ask for one. The read is needed on every press. The waste is reading the whole store to answer it.

**Every reader wants one box's events, not the whole store.** `store/master.py:position_key` composes every key in this file as `f"{box}/{index}"`. The `events` table's `position` column already carries it. It has been indexed since the table's own DDL (`_INDEXES`, `("events", "position")`) on every store on disk. No schema change, migration or version gate is needed.

**The scope is the box, never the bare position.** A wider margin is not the reason. Correctness requires it. A mid-box delete's `renumbered` marker is logged at the DELETED card's own position, not any mover's (D10 ruling 1). So a mover's own reversal must see a line filed under a different position in the same box. That is how it learns a shift happened above it. A position-only scope would answer every ordinary sale, retirement, answer and stand-down correctly. It would silently drop the one case D10 ruling 1 exists for.

**`db.events_at(conn, key)`** answers this with a GLOB query: `SELECT id, payload FROM events WHERE position GLOB ? ORDER BY id`, with `?` bound to `f"{box}/*"`. It uses GLOB, not LIKE. SQLite's optimizer turns a literal-prefix GLOB into a range scan on the `events_position` index, regardless of `case_sensitive_like`. `EXPLAIN QUERY PLAN` on this schema confirms it. It reports `SEARCH events USING INDEX events_position (position>? AND position<?)`. A key that is not `box/index` cannot be box-scoped, so it is never guessed at. It falls back to the full, slow, correct read. It never returns an empty or wrong-scoped list to a caller whose answer feeds a refusal message.

**`Store.history_at(key)`** mirrors `history()` and `named_events()`. All three production call sites that took zero arguments (`_answer_origin`, `_reverse_stand_down`, `_origin`) now call `store.history_at(key)`. This is a pure substitution, since all three already had `key` in scope.

**A second, cheaper change was proposed and is not built, because it is wrong.** The plan called for `_sell` and `do_retire` to skip the read when `undo` is `False`. The premise was that a plain sale or retirement never reads `previous` or `origin_unknown`. It does. Both routes' response bodies carry `"restores_to": None if undo else previous` unconditionally. So the caller learns whether an undo would be offered before tapping it. The skip made `restores_to` return `None` on every plain sale and retirement. `make harness` caught it (`check_mark_sold`, `check_retire`). The skip was reverted. Both routes call `_sale_origin` or `_retirement_origin` unconditionally, as before this decision, now against the box-scoped read.

**`db.history(conn)` and `Store.history()` stay.** They serve the harness's own test-only call sites (about 30, as ground truth for comparisons), any future full-log reader, and the CLI and audit surface if one is added. `events_at` is a sibling, not a replacement. It has the same relationship to `history()` that `events_named` (D134) has, on a different scoping axis: event name there, box here.

**Covered by:** `harness.tests.t7.history_sidecar.check_history_scoped_read`, which checks functional equivalence against the box-filtered slice of a full read, including the `renumbered` cross-box-isolation case. `check_history_scoped_uses_index` asserts that the `EXPLAIN QUERY PLAN` names `events_position`, so the read never falls back to a table scan. `check_mark_sold` and `check_retire`'s corrupt-log cases (`corrupt_history`) now accept a `position` argument. A corrupted row lands inside the box the reversal under test reads from. A `None`-position row, the fixture's prior worst-case default, is invisible to a box-scoped `GLOB`. It would have let those two reversals succeed silently through a corrupt log, instead of refusing.

**Risk carried forward, not resolved here.** A future edit could narrow `events_at`'s `WHERE` clause from `position GLOB ?` (box) to `position = ?` (exact key). Every ordinary reversal would keep working. The one case this decision exists for would break: an undo above a mid-box delete losing sight of the `renumbered` marker. `check_history_scoped_read`'s `renumbered`-visibility assertion is the guard. It must not be simplified away as redundant with the equality check, because that check would stay green under the narrower, wrong scope.

**A second risk, accepted rather than carried forward as a gap.** A corrupt row whose own `position` column is unreadable or absent is `NULL`. It comes from a hand edit or from a write this server never made. Such a row is now invisible to every box-scoped read. `_history` always sets a real `position`, and `position GLOB '<box>/*'` cannot match `NULL`. Before this change, any corrupt row anywhere blocked every reversal in the store, box-scoped or not. That was a wide blast radius. It was also the only thing that made a position-less corrupt row detectable at all. Now a corrupt row inside a box still blocks that box's own reversals, exactly as before. A corrupt row with no recoverable position blocks nothing, box-scoped. This narrows what a hand-corrupted store gets caught doing. It is the trade for not paying the whole store's read cost on every press.

Closing the gap would take one of two things. One option is an unscoped fallback scan for exactly the rows that cannot say what box they are in. That defeats the box scope for the corruption case that most needs it. The other option is refusing every reversal whenever any row in the whole table is corrupt. That is the full-table read cost this decision removes, reintroduced as a full-table integrity check on every press.
