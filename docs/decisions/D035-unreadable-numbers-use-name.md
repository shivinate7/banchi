## D35 — Unreadable numbers fall back to the name

**The owner found it by asking why the review queue held cards that did not need review.** It held 46 entries, every one `no_catalog_row`, every one with **zero candidate rows**. They could not be answered, only skipped. `POST /review/<box>/<index>/answer` refuses an entry with no candidates as `no_candidates`.

**The gap was one line, and its comment stated the false assumption.** When a card had no number, the Pokemon lookup in `pipeline/join.py` fell back to `catalog.rows_for_blank_number_name`. That is an index of **only those export rows whose own `Number` cell is blank**. Its comment: "No collector number on the product (code cards, some promos). These are exactly the rows whose `Number` is blank." That reads `card.number is None` as a fact about the PRODUCT. It is a fact about the READ. The two coincide only while the photograph is good.

Box 2's 544 cards were cropped by a pad that cut the collector number off the bottom of the frame. The crop was fixed in `d431afb`, about 35 minutes after that run was submitted. 37 cards came back with no number at all. Nine came back with a **National Pokedex number read off the artwork strip** (`0326`, `0342`, `0934`, `721`). Every one landed on that fallback, found nothing, and queued as `no_catalog_row`. The export held its row the whole time. It had already matched that row for other copies in the same run.

**Measured against that run's own export, matching by name inside the declared set:** 47 cards carried an unusable number (38 blank, 9 Pokedex-style misreads). ONE of them, `2/7` `Stonjourner`, has since been deleted from the box. So 46 reach the rung, and **45 OF THE 46 RESOLVE TO EXACTLY ONE CARD, WITH ZERO AMBIGUOUS.** The one that does not is a Mega Signal misread as `Mewtwo ex 009/102`. Name and number are both wrong, so nothing can rescue it. It correctly stays `no_catalog_row`.

**These are the counts on disk today.** They were re-checked against disk, not carried forward. Earlier counts read "46 of the 47" and still counted the deleted card. `inventory/parked.json` holds 45 `number_unread_name_matched` entries. `inventory/review.json` holds the single zero-candidate `no_catalog_row`. That is the run this paragraph is about.

**The name is the more reliable field, which is the argument for the whole rung.** T1's recorded misses are `051/197` for `031/197` and `271/167` for `211/167`. These are confident answers with the name right and the digits wrong. `docs/GATES.md` says no confidence threshold fires on those. The same shape produced all nine of box 2's wrong numbers. A rung that trusts the name when the number finds nothing is not a weaker check. It is the check aimed at the field that survives.

**It fires only on an empty result, and both emptiness cases count.** A number that matches rows is never second-guessed. Four of box 2's misreads carried a denominator too. They composed a well-formed key that matched nothing and stopped there. So an empty NUMBER lookup falls through as well as a missing one. It cannot mislist anything. It is reached only when the card was bound for `no_catalog_row` regardless. It produces a queue entry, not a listing.

**`CLAUDE.md`'s HARD RULE is NARROWED, NOT REPEALED**, and this paragraph is the narrowing. That file says "Never join on Product Name — it inconsistently embeds numbers." It is right, and the inconsistency is live in the owner's own data. Box 2's export writes `Delibird - 105/132` and `Nickit` in the same column. The first pass at the measurement matched raw names and scored 35 of 46 instead of 46 of 47. So the rule now reads: **never as the primary key. Permitted as a last resort that fires only when the number key finds nothing. Folded on both sides by `join.name_index_key`, which strips a trailing ` - <n>/<total>` and the case. Never able to list a card on its own.** `name_index_key` is `number_index_key`'s twin. It exists for the same reason: two sources spell one identity differently, and neither is wrong.

**A card found this way is queued, never listed. That is the owner's ruling.** Listing was offered and declined. The owner wants to bulk clear such entries when they all belong to one claimed set. The owner has an Excel for that set, and the names match exactly. The field that tells one card from another is the field that could not be read. So the last check is a person looking at the photograph.

**It costs one press, not one per card, and that is why queuing is affordable.** Every entry from this rung carries **one** candidate, the row the ladder chose, under **one** shared reason. A uniform stack gives **one** shared condition string. That is exactly D29's group-answer eligibility. Box 2's 45 are one `G`, one Enter, and one `U` to reverse, over a grid of their photographs. No new screen and no new route. `routing.NUMBER_UNREAD_NAME_MATCHED` plus a label was the whole client change.

**The lookup string says `name?:` and not `name:`.** A row found because the product prints no number and a row found because we could not read one are different facts. They have different remedies. Both are printed on the RUN REPORT (D16; the machine string stays greppable).

**It does NOT reach the queue entry.** This entry once claimed it did. `store/queues.py:QueueEntry` has no `lookup` field, and `Queue.parse` drops unknown keys. So the string lives only in `JoinReport`'s output. A name-inferred card that does NOT resolve cleanly (`set_ambiguous`, or any ladder review reason) never reaches the block that stamps `number_unread_name_matched`. Its queue entry carries an ordinary reason. Nothing records that the row set was reached by name. The review screen draws its "matched by name" sentence from that reason code alone. So such a card looks the same on screen as one whose number read fine. Carrying the lookup onto `QueueEntry` is the fix. It is a schema change nobody has argued for yet.

**What would reopen this: a name that resolves to two cards in one set.** Measured at zero across box 2, but a set with two prints of one name would produce it. The behavior is already correct. Two surviving rows means two candidates and an ordinary one-card review. It has never been seen. The group offer would correctly refuse it as `group_not_uniform`.

**It was a rule about Pokemon's lookup alone, and it was written as a rule about a read.** This entry argues that the NUMBER is the field that fails and the NAME is the field that survives. That is a claim about photographs and models, with nothing game-specific in it. It was nevertheless implemented in the Pokemon lookup alone. Every game keyed by a printed identifier (`riftbound`, `one_piece`) returned an empty row set. It stopped where Pokemon fell through to the name.

**The owner found the gap from the far end.** The owner asked why cards whose rows were plainly in the export sat in the review queue as unanswerable. Run `2026-08-29-box1-01` holds 133 real Riftbound cards. It had **4 unusable reads, all 4 zero-candidate `no_catalog_row`.** A zero-candidate entry is refused by `POST /review/<box>/<index>/answer` as `no_candidates`. Those cards could not be answered at all, only skipped, every session. Three carried a set-code prefix the Riftbound prompt forbids. Examples: `UNL • 140/219` for `140/219`, twice with a bullet and once with a middot. That is a model slip at 3 of 133, not a prompt gap. All three hold exactly one row by name. One of them, `Hwei, Brooding Painter` at **$2.86**, is above D9's threshold. It is a listable card stuck unanswerable. The fourth read `Wuju Master` for the export's `Master Yi, Wuju Master`. It correctly stays unmatched. The name it gave is not the name the export carries, so nothing can rescue it.

**Nothing about the rung is widened by this.** It still fires only on an empty result, so it is reached only by a card already bound for `no_catalog_row`. It still produces a queue entry and never a listing. It still answers `name?:` rather than `name:`. What changed is which strategies run it. `name_only` deliberately does NOT gain it. There the name IS the key, so there is no unreadable number to fall back from.

**The real finding was the shape, and it is fixed, by the owner's ruling the same day.** Each game had its own `_lookup_*` function. Each re-implemented the same four-step ladder: build a key, look it up, try the blank-`Number` name, fall back to the name. They differed only in STEP ONE, the only genuinely per-game part. This entry landed in one copy, and nothing compared them, because nothing could. They were three unrelated functions that happened to be parallel.

`pipeline/join.py:_walk` is now the ladder, written once. `KeyStrategy` is the per-game part as a VALUE: a key builder, the lookup label, and whether this entry's rung applies. **A rung added to `_walk` cannot land in one game and not another.** The old shape could not offer that property at any level of care.

**The owner asked whether the exports differ per game. They do not.** Measured across all four committed fixtures (SV09, the wide Pokemon export, Riftbound and One Piece), the 16-column header is **byte-identical**. One md5 covers all of them. That is what makes a shared ladder correct rather than merely tidy. What is genuinely per-game is the `Product Line` cell, the rarity vocabulary, the shape of the `Number` cells, and one import file per game (D25). None of that lives below step one.

**`name_only` keeps its exemption, and it is not compatibility debt.** `pokemon_code` has no collector number at all. It lives inside the Pokemon export as a blank-`Number` row. So `rows_for_name` would match it to the NUMBERED card of the same name: a code card listed as the card it came with. The rung is for "we could not READ the number". A product that prints none has nothing to fall back from. That is now a declared `name_rung=False`, not an absence somebody has to notice.

**Behavior-preserving, and checked as such rather than asserted.** `join --dry-run` over both real runs, box 1's 133 Riftbound cards and box 2's 544 Pokemon cards, produced **byte-identical output** before and after the restructure.

Covered by T3 in both directions, observed failing against the old code first.
