## D270 — One filter bar for every list

**One filter bar, `kit/filters.tsx:FilterBar`, serves every filtered list.** It is built on Capture's own picker pattern (kit-data's `Select`, `FilterChips` and `SortControl`). It opens the kit's own panel and never opens the OS menu. It is search plus one `Filters` trigger with a count badge, at every width. It carries any facet a screen hands it, in any order.

The old wide-bar rule is gone. A container query used to choose an inline row or a sheet. The owner judged the wide case a defect too. Fitting is not the same as deserving the room.

`compact` (default `'popover'`) picks what the trigger opens. On a desk that is a floating `Popover` (`kit/overlay.tsx`, anchored to the trigger). On a phone it is the kit's `Sheet`. A caller that knows its width is phone-sized passes `'sheet'`. Nothing in the kit reads `matchMedia` or a container query for this. A kit specimen bar measures 70px at 1440 and 90px at 720 and 390.

- **What the bar does.** It shows a count per option under the other active filters. It draws a zero and never hides it. Single-choice and multi-choice facets are marked differently. Each facet has a clear. There is one clear-all, the count line's, since `FilterChips`' own "Clear all" is not drawn inside a bar. There is no order lock, and no facet wipes another's choice. Every control has one height. Every facet trigger shares one width: the widest any needs, in one grid track. A pick never changes that width (D118). "N of M" is drawn by construction. `FilterCount` cannot be left out. It names every narrowing: each pick, the search's words, and the hide toggle while it hides a row. The trigger's badge counts only what differs from the screen at rest, so a Hide sold that is on by default (D132) is not counted. A slot beside the search holds one control of the screen's own. The search's busy and failure states come from `useSearch`.
- **Counts come from one helper.** `kit/facets.ts:countFacets` counts, for each option, the rows the list would show under the other active facets. It applies the screen's own search and hide toggle. `withCounts` takes the same answer from the server.
- **One `HideToggle` replaces three shapes.** Those were "Hide sold"'s pill, "Hide never-seen SKUs"' bare checkbox, and "Holding"'s dimming chip. It is a field-edged control at the bar's own height. Its check mark fills with the accent when on. It shows a count beside its words. A pressed `Chip` was refused: it filled black in light and white in dark, the heaviest object in the bar, for a state that is on by default. A bar takes several toggles through `hide`.
- **One `SortHeader` marks the active column in two channels.** The label goes to full ink weight. The one chevron drawn belongs to it. The old pattern drew a chevron on every header. `aria-sort` sits on the `<th>` itself, never on the button inside. Each column has its own first direction (a name starts A to Z).
- **Retired premises.** D213's native `<select>` for Set: Set and Rarity were disabled until Game was chosen, and `BoxBrowse.tsx:setGameFilter` reset them on every Game change. The aim of one control that reads the same for every game is kept. Facets never disable each other. D220's native Status select and toolbar had four controls in four widths and two heights, and Status opened the OS menu. The desk keeps the one-line fit. A phone folds the same controls behind one trigger, since D195 says same-role controls share a width. D132's pill and D296's checkbox chose two shapes for one idea. No earlier decision set one filter control for the app.
- **A page header holds at most one worded primary.** The rest of a header's actions are `IconButton`s or a More menu. `make kit-adoption`'s `R2-header-actions` rule checks this. `R2-filter-row` refuses a screen built by hand from `SearchField` and a facet control, in place of `FilterBar` (`scripts/kit-adoption.mjs`). Offenders are in `scripts/kit-adoption-allow.json`, keyed to their lane.
- **Inventory's rail uses the bar.** Game, Set and Rarity each take several picks in any order. No pick clears another. The picks live in the URL. `GET /boxes` sends `facet_cells`: the store's cards grouped by box, game, set, rarity and whether they left. The screen folds them with `countFacets`, so a pick asks the server nothing. The unclassified value is the blank pick, `?set=`.
- **Orders.** There is no hidden base. What the bar shows is what the list is. "Show" is multi-choice. Within a facet it is OR, and across facets it is AND. It carries an explicit "Open" pick, selected at rest, beside "Done". Empty Show lists every buyer, open and done. Open plus Done lists both. "Done" reads the closed groups. "Open" reads the open ones. Every other value (Flagged, Short, Partly picked, and so on) reads the open ones in that state. So a narrowing pick with Open is the union. The pick to narrow with is made after clearing Open. "Hide unpullable" is on at rest and shown on in the bar. It cuts open buyers with no card on hand to pull, never done ones. It is a toggle, not a Show pick. A Show pick is a state a buyer is in. Search narrows within exactly what the bar shows, so a done buyer is found once Done is in or Show is cleared. Each option counts under the other facets. The rest view needs no query string. The Filters badge counts only a move from rest. The URL round-trips picks (`?show=a&show=b`, `?show=` for none, `?pullable=0`). There is no device key, since the URL is the memory. A link that names a state, status, buyer, order or search opens wide enough to show it. It sets Show empty and Hide unpullable off, and reads the link once, at mount. `?order=` takes the store key or the order number. A number two buyers share opens neither, and a notice says so. One state has one name across the facet, the row pills and the sort: "Check", "Unresolved", "Missing", "Status" and "Hide unknown". The sorts are "Value", "Cards", "Buyer" and "Fewest drawers".

Open: which facets each screen passes and in what order, and the word for "Any" per screen.
