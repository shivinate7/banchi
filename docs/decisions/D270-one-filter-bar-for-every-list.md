## D270 — One filter bar for every list

**One filter bar, `kit/filters.tsx:FilterBar`, serves every filtered list.** It is built on Capture's own picker pattern (kit-data's `Select`, `FilterChips` and `SortControl`), opens the kit's own panel, and never opens the OS menu. It is search plus one `Filters` trigger with a count badge at every width, and it carries any facet a screen hands it, in any order. The old wide-bar rule, a container query choosing an inline row or a sheet, is gone. A wide bar had room, but fitting is not deserving the room, and the owner judged the wide case a defect too. `compact` (default `'popover'`) picks what the trigger opens: a floating `Popover` (`kit/overlay.tsx`, anchored to the trigger) on a desk and the kit's `Sheet` on a phone. A caller that knows its width is phone-sized passes `'sheet'`. Nothing in the kit reads `matchMedia` or a container query for this. A kit specimen bar measures 70px at 1440 and 90px at 720 and 390.

- **What the bar does.** It shows a count per option under the other active filters, and draws a zero and never hides it. A single-choice and a multi-choice facet are marked differently. Each facet has a clear, and there is one clear-all, the count line's, since `FilterChips`' own "Clear all" is not drawn inside a bar. There is no order lock, and no facet wipes another's choice. Every control has one height, and every facet trigger shares one width, the widest any needs in one grid track, which a pick never changes (D118). "N of M" is drawn by construction: `FilterCount` cannot be left out and names every narrowing (each pick, the search's words, and the hide toggle while it hides a row). The trigger's badge counts only what differs from the screen at rest, so a Hide sold that is on by default (D132) is not counted. A slot beside the search holds one control of the screen's own, and the search's busy and failure states come from `useSearch`.
- **Counts come from one helper.** `kit/facets.ts:countFacets` counts, for each option, the rows the list would show under the other active facets, with the screen's own search and hide toggle applied. `withCounts` takes the same answer from the server.
- **One `HideToggle` replaces three shapes** ("Hide sold"'s pill, "Hide never-seen SKUs"' bare checkbox, "Holding"'s dimming chip). It is a field-edged control at the bar's own height whose check mark fills with the accent when on and which shows a count beside its words. A pressed `Chip` was refused: it filled black in light and white in dark, the heaviest object in the bar, for a state that is on by default. A bar takes several toggles through `hide`.
- **One `SortHeader` marks the active column in two channels:** the label goes to full ink weight and the one chevron ever drawn belongs to it (the old pattern drew a chevron on every header). It is the `<th>` itself and `aria-sort` sits on it, never on the button inside. Each column has its own first direction (a name starts A to Z).
- **The premises it retires.** D213's native `<select>` for Set (Set and Rarity were `disabled` until Game was chosen, and `BoxBrowse.tsx:setGameFilter` reset them on every Game change): the aim of one control that reads the same for every game is kept, and facets never disable each other. D220's native Status select and toolbar (four controls in four widths and two heights, and Status opened the OS menu): the desk keeps the one-line fit, and a phone folds the same controls behind one trigger, since D195 says same-role controls share a width. D132's pill and D296's checkbox chose two shapes for one idea. No earlier decision set one filter control for the app.
- **A page header holds at most one worded primary.** The rest of a header's actions are `IconButton`s or a More menu. `make kit-adoption`'s `R2-header-actions` rule checks this, and `R2-filter-row` refuses a screen built by hand from `SearchField` and a facet control in place of `FilterBar` (`scripts/kit-adoption.mjs`). Offenders are in `scripts/kit-adoption-allow.json`, keyed to their lane.
- **Inventory's rail uses the bar.** Game, Set and Rarity each take several picks in any order, and no pick clears another. The picks live in the URL. `GET /boxes` sends `facet_cells` (the store's cards grouped by box, game, set, rarity and whether they left), and the screen folds them with `countFacets`, so a pick asks the server nothing. The unclassified value is the blank pick, `?set=`.
- **Orders.** There is no hidden base: what the bar shows is what the list is. "Show" is multi-choice (OR within a facet, AND across facets) and carries an explicit "Open" pick, selected at rest, beside "Done". Empty Show lists every buyer, open and done. Open plus Done lists both. "Done" reads the closed groups, "Open" the open ones, and every other value (Flagged, Short, Partly picked, and so on) the open ones in that state, so a narrowing pick with Open is the union and the pick to narrow with is made after clearing Open. "Hide unpullable" is on at rest and shown on in the bar. It cuts open buyers with no card on hand to pull, never done ones. It is a toggle and not a Show pick, since a Show pick is a state a buyer is in and this is a cut across states. Search narrows within exactly what the bar shows, so a done buyer is found once Done is in or Show is cleared. Each option counts under the other facets. The rest view needs no query string, the Filters badge counts only a move from rest, and the URL round-trips picks (`?show=a&show=b`, `?show=` for none, `?pullable=0`). There is no device key, since the URL is the memory. A link that names a state, status, buyer, order or search opens wide enough to show it (Show empty, Hide unpullable off), read once at mount. `?order=` takes the store key or the order number. One state has one name across the facet, the row pills and the sort ("Check", "Unresolved", "Missing", "Status", "Hide unknown"; sorts "Value", "Cards", "Buyer", "Fewest drawers").

Open: which facets each screen passes and in what order, and the word for "Any" per screen.
