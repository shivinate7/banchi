## D252 — A wrong answer gets a correcting route

**A wrong answer that already went out cannot be undone (`undo_too_late`, D28), so a listed card gets its own correcting route, `POST /inventory/<box>/<index>/correct`.** It rebinds the SKU through `bind_sku` and never writes stored fields by hand. The SKU it leaves is over-listed by exactly what it gave up, and a departed card refuses (`card_departed`). It is not a branch on `do_review_answer`: `_answer_target` refuses `not_in_queue`, and a wrongly answered card holds no queue entry. `sku_unchanged` stays, and a sibling confirm press covers "the SKU is right and the drawn name is wrong" (D258). Undo derives the identity again and does not restore stored values.

- **The new SKU is re-read on the server** from `_catalog_for_card`'s export inside the write lock, as a D77 `from_catalog` answer is, and the wire is never trusted (`sku_not_in_catalog`). It gets no listing write: choosing a row is not pushing one, and `emit` does that (D54).
- **The old SKU is released through `Listing.release` (D34).** `pushed`, `staged` and `live` are counts on a SKU and never addresses (D7), so one copy of the least-committed stage is given up, `pushed` then `staged` then `live`. `pipeline/livecheck.py:compare` (`reconcile --live`) reads the leftover into D109's `beyond` bucket, TCGplayer's own quantity for a SKU this pipeline never sent. `check_correct_answer` proves it against the real module: a live export naming the old SKU's still-live copy lands in `report.beyond`, neither `agreed` nor `unexplained`. Nothing uploads to TCGplayer, and the next `reconcile --live` says what to lower by hand.
- **The stored identity follows the catalog:** `card.name`, `set_name`, `rarity`, `number` and `printed_total`, from the same row and transaction. `_catalog_row` must carry `rarity` (it lacked the key, so `chosen.get("rarity")` always answered `None`, in this route and in `do_review_answer`'s `from_catalog` branch; T7 asserts both). Splitting the number is game-aware through the game's own key strategy: `pipeline/join.py:catalog_number_fields(game, raw_number)` reads `games.get(game)["join_key"]`. A `number_and_printed_total` game (Pokemon) splits through `store/numbers.py:split_catalog_number` on the last `/`, since a secret rare's numerator can be `302*`. Every other strategy (`printed_code`, `name_only`, `not_joined`) stores the cell verbatim with `printed_total` empty. Riftbound reads `card.number` whole, so splitting `056/298` would break a store-backed join (D188), fill `number_key` wrongly and mishandle 13 double-sided `T01 // T02` cells. `_catalog_answer` returns the game beside the row, so nothing re-parses the export. `number_key` and `number_display` are never set directly (`store/master.py:_card_columns` derives them). D36 and D183 do not govern this field, and the model's own reading stays in `identifications.json`.
- **Undo goes both ways (D28's shape).** `{"undo": true}` reads back the overwritten pair. `restores_to` carries `sku`, `condition`, `set_name`, `rarity`, `name`, `number` and `printed_total`, and a missing key is not a `null` claim: `_reverse_correction` checks presence, or an older line would erase a real number it never touched. The released copy goes back through the SKU's public writers (`bump` for `pushed` and `staged`, `set` for `live`, which `bump` refuses, D115), with `staged_at` and `live_as_of` restored at their pre-correction values so the round trip is not a fresh reading nobody took (`check_correct_answer_live_release`). The card is the ground truth for whether there is something to reverse (its `sku` and `condition` still match the newest `sku_corrected` line). `undo_too_late` is checked on the card's current SKU. The events are `sku_corrected` and `sku_correction_undone`, never `answered` or `corrected` (D3's claim edit).
- **The screen shows on `#/inventory` only.** `app/src/CardHero.tsx`'s `ListingCorrection` sits inside `CardDetailsSection`'s `correctable` prop, which defaults false, an allow-list of one screen that `BoxBrowse.tsx` sets. It shows only for an identified, on-hand card (the route's own refusals `not_identified` and `card_departed`), reuses D77's picker (`CatalogPanel`, `CandidateButton` exported from `ReviewQueue.tsx`), and is followed by a receipt with Undo. Its words are "Wrong card?" and "Correct the listing." (D196). The slot keeps its height when the card leaves eligibility (D118): the wrapper always renders and `min-height` reserves the height, since a vanished control shrank the Details panel by 44px.

Correcting a sold card's SKU is a larger question (`sold_here`, a buyer's order) and is not attempted.
