## D73 — A stale screen re-reads when the operator returns

**Two questions look alike.** `X-Pkmnscan-Boot` (`BOOT_ID`, `noteBoot`, `onServerBoot`) answers whether the code changed, and it rides traffic that exists because a restart happens while the operator works. Nothing can answer whether the data changed. A screen goes stale because nobody touches it, so it has no traffic to ride, and a data-generation header is what the boot header's own design says cannot be had.

- **The reading is unsafe, not the write.** Under D58 a stale number names a different card, and the operator counts to it in a drawer and pulls the wrong one. The stored index never moves, so a stale screen's write still lands on the record it names. The phone's `UndoTarget` label goes stale too.
- **Re-read when the operator returns, never re-render while they are on the screen.** `app/src/Fulfillment.tsx` is the idiom: re-read on coming back and on finishing a sale, never on a timer that reorders a list under a thumb (D28). Every route change unmounts the view, so arrival is a full re-read. Polls go through `usePoll` (D207). `#/review` never re-renders mid-session. `#/inventory` is the urgent case, because a capture from the phone changes the labels the walk draws. A notice with a control is refused (`docs/DESIGN.md` bans acknowledgements).
- **No live connection.** Every verb funnels through `_dispatch`, which counts requests in flight, so a held stream turns each watched Python save into a 35-second stall, a 40-second grace and a SIGKILL. `REQUEST_SLOTS = 4` makes one stream a quarter of the server's capacity. `app/tests/cursor.spec.ts` waits for `networkidle` inside a `.catch`, so an open stream keeps the suite green and about three and a half minutes slower. A WebSocket adds a dependency to the one process that may never need `make venv`.
- **A signal would be a monotonic counter in `store/session.Store`,** the funnel every mutation passes through, coalesced (the feeder fires at a 623 ms median, so per-generation events become furniture). A random id like `BOOT_ID` cannot be compared or coalesced. It is banked, not built.
- **`markSold` and `undoSale` take `(box, index)` and carry no aim check.** Only `removeCardInPlace` and the order pull are `capture_id`-aimed. The wire does not refuse a stale press.

Reopen for a second pair of hands. A real Fulfiller and the owner writing at once is too fast for return-to-screen.
