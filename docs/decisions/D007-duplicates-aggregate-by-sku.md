**A cap never stopped a copy being sent twice.** That is what makes removing it safe. The `add_to_quantity` docstring splits the jobs. `committed_positions` keeps a copy out of the sellable set. The cap reads a quantity. Removing the bound removes exposure limiting only. `uncommitted_positions` is untouched. It still makes a re-emit a no-op.

**The figure survives as an offer, not a default.** `pipeline/pricing.py:LIVE_QUANTITY_CAP` is still 4. A press may still propose it. A send no longer inherits it. ~~`policy.live_cap` remains for a store that wants a standing answer. It reads `None`, meaning no cap, when nothing has written one.~~

**The standing key is deleted (amended 2026-09-08, operator's instruction).** The operator ruled that caps live per send only, with no standing key. The struck clause was the implementer's addition. The operator chose a control on the run. It says "cap this send at N" before the file is written. It is opt-in and per send, so nothing standing changes. A standing key would be a change.

**A store that still holds the key is refused by name.** It is never silently uncapped. Ignoring the key would drop a bound the operator asked for, and say nothing. Silence is the harder failure here. `Corpus.parse` rebuilds `policy` from named fields. `keep` preserves only unknown TOP-LEVEL keys. **What the deletion kept.** `policy.per_run` survives with its other four keys. `policy_for` folds the override over a `standing` dict. `#/pricing` writes a per-run `threshold`, and narrowing the fold would lose it. `SearchGroup.cap` and `PricingWorklist.live_cap` left the wire. The `cap` and `listable` pair let a screen draw the rule or what the rule allowed. With no rule, there is one field.

**A default-built corpus carried the retired bound (fixed 2026-09-08).** `Corpus.parse` read an absent key as `None`. But `Corpus.live_cap`'s dataclass default stayed `LIVE_QUANTITY_CAP`. `to_payload` writes that key unconditionally. So a default-built corpus carried four. The first save of a fresh store wrote the retired bound into `policy`. `server/pipeline_routes.py`'s fallback, for a corpus it could not read, invented a cap nobody set. `live_cap_for`'s except arm was changed to stop doing this.

**It hid a second defect.** `pipeline/merge.py` merged legs' caps with `max(leg.match.live_cap for leg in legs)`. That was total while the field was an `int`. Once this entry was rewritten, it compared against `None`. It raised `TypeError` on the shape a merged send exists for: a SKU held by two or more runs. Nine harness tests and a full `make check` stayed green. Every case ran on a store whose corpus default still answered four. Correcting the default made the crash reachable. `t7:check_merged_emit_uncapped` now reaches it.

**The merge took the wrong cap.** `max` returns the LOOSEST bound. A send spanning a run held to 2 and a run at 4 offered 4. Every other cross-run rule in that module is conservative. `_merged_cap` takes the smallest cap any leg names. `None` never outranks a figure. No bound is not a large bound.

**The figure is a ceiling on copies live.** `add_to_quantity` is `live_cap - copies_out`. That is D59's arithmetic, and it is right. A SKU with seven copies already at TCGplayer and a figure of four adds **nothing**. The control read "at most N of each card". `--cap N` read "send at most N copies". Both describe a send quantity, which is a different control. Measured on a ten-copy SKU with seven out, every figure from 1 to 7 wrote no row.

**The cap counts the copies the live guard sees (amended 2026-09-25, a defect fix).** `emit --cap N --live-guard F` spent the cap against `copies_out` alone. That figure reads the store and the join's export. When `F` showed more live copies than either, the cap did not move. So `--cap 1` over one live copy sent one more, with two live. `cli/cmd_emit.py:_apply_guard` wrote the guard's count to `SkuMatch.guard_live`. `copies_out` and `live_now` took the larger reading. `pipeline/merge.py:_merged_match` took the largest reading of its legs. The one-run and several-run paths then agreed. The send route passes no `--cap`, so it could not reach the defect. T7's `check_send_matrix` pinned it in the `capguard/*` rows. Those cover live copies below, at and over the cap, on both paths. Each row was red on the unfixed emit.

**Larger reading, not the sum (owner ruled 2026-09-25 to take the larger reading).** For the cap, the sum is the safe direction. The two readings can count different copies, so the true count out is their sum. But a pending copy that has landed is in both readings. The sum counts it twice. It under-sends on each ordinary re-send. The larger reading never counts a landed copy twice. It can overshoot the cap by up to the number of pending copies. The rule below replaces this one.

**The guard's reading is its own field, so a trim stays a trim.** `_would` measures the send without the guard, through `SkuMatch.unguarded_room`. The first version wrote the guard's count into `held_out`. Under a cap, that closed the room before the trim was measured. A card the guard trimmed then read as "asked for none". The headline said every card needed a price. Rows `share/{one,two}/cap1-guardall` pin it. Both were red on that version.

**The mismatch was survivable only while the cap stood.** A bound of four over everything kept `copies_out` near it, so the two readings agreed in practice. A per-send cap made uncapped the default. `copies_out` now grows with every press. The subtraction then answers zero for any SKU ever sent. That is the ordinary case, not the corner.

**The rule above is replaced (owner ruled, 2026-09-27).** The operator ruled that capping is available only once a send is reconciled with live. Asked to choose between "the larger" and this rule, the owner chose this one. It replaces the 2026-09-25 amendment. It does not sit beside it.

**`emit --cap` now refuses a card outright while a copy sent since is still pending.** It no longer spends the cap against either reading. Each reading can be wrong alone. Measured overshoots: one pending copy and one unseen live copy, under a cap of 2, sent a third. Three pending copies with four live, under a cap of 5, sent an eighth. "Pending" is not a new clock. It is `nothing_to_add`'s arithmetic, `copies_out - live_now`. `cli/resolve.py:_copies_out` computes both halves. `SkuMatch._cap_pending` reads that gap as a yes-or-no answer. It is not a second copy of the sum.

**Once a SKU is not pending, the store's `live_now` is the true count.** The cap is spent against it alone. `copies_out` and `live_now` no longer read `guard_live`. `SkuMatch.guard_live` and `unguarded_room` are deleted. No second reading is left to max or sum. The refusal names the remedy in the screen's words: "N copies sent and not yet seen live — read what is live, then send again".

**The refusal is only as true as `_copies_out`.** A zero reading means not live (D150). A copy stuck in TCGplayer's Staged list is out of scope by the owner's choice. So `_cap_pending` can read "not pending" on a card TCGplayer still holds.

**The guard file (`emit --live-guard`) keeps its other job.** `cli/cmd_emit.py:_apply_guard`'s `sendguard.room` trim, applied to `asked`, still bounds a send to what is physically on hand. It runs whether or not a cap is asked for.

So the guard's zeroing of `asked` read as "this send asked for none of this card". Those are the operator's own words, for a zero the operator never typed. `SkuMatch.guard_trimmed` tells the two apart. It is set only in `_apply_guard`. `nothing_to_add` now uses the words the visible trim already uses: "TCGplayer already holds every copy on hand". **A number on each card's row is a send quantity (amended 2026-09-11, on the operator's report).** The operator reported that quantities could no longer be selected to sell. ### Copies are fungible, and `live` is a quantity, not a set of addresses

Amended 2026-08-23 by the owner. This entry used to say order pulls select specific positions. `cli/cmd_join.py` implemented that literally. It walked `positions_for_sku`, kept the staged copies, and promoted the first N. So four of seven identical cards were sellable and three were not. The owner ruled that any copy may be live, not specific positions. If 3 of 15 copies are marked live, any 3 are live.

So the three listing stages moved off the card and onto the SKU:

- A position's `state` is `captured`, `identified` or `sold`. It describes one physical card. `pushed`, `staged` and `live` are no longer in `master.STATES`. `check_state` refuses them. That stops a caller using the old `set_state(key, LIVE)` and getting a per-position flag back.
- `store/master.py:Listing` holds `pushed`, `staged` and `live` as counts per SKU.
- **Every unsold copy is sellable.** The pull marks whichever copy the hand reached. A sale is COUNTED AGAINST the SKU's reading. It does not edit that reading (D115). `live` is what the last export said. `sold_here` is what has sold here since. The figure on screen is the difference, floored at zero. It used to decrement `live` directly. That is how one copy was subtracted twice. An export that already knew subtracted it once. The sale subtracted it again.
- Copies on hand is a count of unsold positions. Listed quantity is `min(cap, on hand)`.

**That `min` reached the pipeline, not the screen, until the owner caught it (2026-08-25).** `pipeline/join.py:add_to_quantity` has always bounded by copies held (`min(room, uncommitted)`). But `GET /search` sent the bare `LIVE_QUANTITY_CAP`. `CardLocations.tsx` drew it as the denominator of `listed N of ...`. A card the owner had one of read **`listed 0 of 4`**, beside `on hand 1`. The cap was not wrong. The fraction was wrong. A denominator reads as what is achievable. Three of those four copies do not exist. D20 names this failure at box scale. Here it was at SKU scale.

`SearchGroup` now carries **both**. `cap` is the rule. `listable` is `min(cap, on hand)` for that SKU. The server computes it. `app/src/server.ts` records that the app may not compute the live cap. A `Math.min` in TypeScript would keep the rule in two places. T7 asserts the arithmetic, not the literal, so it moves when the cap does.

**The decrement is an optimistic local estimate, and that is not a weakness.** D8 and D11 put the authority in the TCGplayer export's `Total Quantity`. `join` reads it on every run. So this number was never a second source of truth. A run corrects any drift a between-run sale introduced. The failure this ordering prevents is the opposite one. It holds the count back until a join. Then the app disagrees with the shelf the operator is standing in front of.

**Backstock is a number, not a place.** "Excess copies are backstock at known positions" stays true in the only sense that matters. Every copy is at a known position, and the app maps SKU to all of them. No copy is *designated* backstock. Nothing may reintroduce a per-position listing flag to make one.

### The map was false for every copy past the fourth

The owner found this on 2026-08-30. `cli/cmd_emit.py` wrote the card's identity (`sku`, `condition`, `run`) inside a loop. The loop ran over `SkuMatch.live_positions`, which is `uncommitted_positions[:add_to_quantity]`. So it was bounded by the `live_cap` of 4. The cap reached the record. The record is how many copies of a card we know the name of.

The owner's words on finding it, paraphrased: a gentle heads-up to list four by default, mainly for cheap cards. It took a different shape. The cap is a rule about the LISTING, meaning the envelope-buster order and the stale-price spike above. It had become a rule about the RECORD.

**An unstamped copy is not backstock as defined above.** Backstock is a number, and `backstock_positions` is a real answer this pipeline computes. A copy with `sku: null` is something else. It is invisible to `GET /search`, absent from `positions_for_sku`, and uncounted by `copies_on_hand`. The map this entry promises did not contain it.

**Measured on the owner's store the day it was found:** Rengar, Trophy Hunter (9189797, $30.81) holds SEVEN copies (3/1, 3/2, 3/4, 3/17, 3/20, 3/30, 3/36). Four carried the SKU. The screen reported four on hand for a card with seven. The three it could not see were the most valuable cards in the box.

**The stamp runs over `uncommitted_positions`. The count runs over `live_positions`. Keeping them apart is the fix.** `pushed` is a commitment that a CSV row was written. A backstock copy has no row. One increment serving both loops would push the count past `add_to_quantity`. It would double-stage on the next import. `docs/GATES.md` records that failure from the first real post-import re-emit.

**It is `uncommitted_positions`, not `positions`. The other choice would have made the fix worse than the defect.** The obvious repair is to iterate every matched position, and that destroys data. `cli/resolve.py` marks a copy committed on either of two grounds. One ground is a count read back off the `Listing`. The other is the copy being in a TERMINAL state. So every sold and retired copy of a matched SKU sits in `match.positions`. `store/master.py:set_state` has no terminal guard. Iterating them would move a sold card to `identified`. That loses D10's permanent gap and D26's terminal state, silently. Measured on the same run, **eight of its 33 matched positions are sold**. One re-emit would have resurrected all eight. `uncommitted_positions` cannot contain a departed copy by construction.

**Excluding the committed ones loses nothing.** A copy committed by COUNT was chosen by `_committed_keys` from `copies_on_hand`. That list selects on `sku`, so the copy is already stamped. A copy committed by having LEFT is not this command's to relabel.

**Idempotence is untouched.** It lives in `cli/resolve.py:_committed_keys`, which reads the `Listing` counts and never `card.sku`. Widening what gets stamped cannot change what gets pushed. D54's rule that a re-emit adds and never subtracts still holds.

**What it recovers is small today and structural from here.** Three cards on the owner's store, Rengar's backstock. Only two runs were ever emitted, and only one SKU in them holds more copies than the cap. Of the 715 records, 502 carry `sku: null`. **498 of them are box 2, whose run was joined and never emitted.** That is a different gap with a different remedy.

**A second effect, smaller than first claimed.** `_committed_keys` slices `copies_on_hand(sku)[:held]`. An unstamped copy is missing from that list, so the slice can return fewer keys than `held`. That under-counts `committed_positions` and inflates `add_to_quantity`. Full stamping makes the list complete. It fixes nothing on the store today. Four SKUs are short now, and all four are short because their stamped copies SOLD. A sold copy is committed by the terminal branch, so the count is right anyway. Recorded as a hole closed, not a bug fixed.

**Covered by T7's `check_emit_identity_stamp`, in its own isolated home.** Seven copies of a holofoil-only number are the case. Every copy carries the SKU. `pushed` stops at the cap. The import file asks for exactly the cap on one row. A sold copy survives a re-emit. Three mutations were seen failing before it was kept. They were the original `live_positions` loop, the naive `match.positions` loop, and a shared increment. Each was red on a different assertion.

### The cap itself is the owner's next question. Recorded, not built

On 2026-08-30 the owner was shown the fix above. The owner was also shown the note that a value-dependent cap was the other half of their instruction. They would like the cap to depend on value. For now the flat 4 stands. This paragraph marks that it stands by default, not by argument.

**What is questioned is the flatness, not the cap.** The reasoning above is untouched. A cap still blocks the envelope-buster order. It still bounds how many copies a price spike sells at a stale number. The owner doubts one number serving every card. The concrete case is Rengar at **$30.81**, capped at four by a default reasoned about with commons in mind. D9 draws the same line one register over. There, the threshold and the floor are derived from a labor bar, not picked. A cap derived the same way would be a number with an argument behind it. It would not be a constant nobody has revisited.

**When it is made, it is a change to THIS ENTRY, and the shape is already here.** `SkuMatch.live_cap` is a per-match field with `LIVE_QUANTITY_CAP` as its default. `pipeline/join.py:build` takes `live_cap` as an argument. So a rule that reads the row's own market price has a place to live. It needs no schema change and no new wire field. The argument is still open. It needs the bands. It needs the cap in each band. It needs a choice: a per-run setting like D9's sub-threshold disposition, or a standing rule. None of that is argued. A cap that varies is a cap an operator must predict. So the screen half is part of the question, not a follow-up.

**Nothing is blocked on it, and nothing should wait for it.** The defect above was that the cap reached the RECORD. That is fixed, whatever the cap becomes. The identity write no longer reads `live_cap` at all. This decision can be taken later without touching that seam again.
