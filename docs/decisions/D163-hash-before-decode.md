## D163 — Identify hashes first, decodes on a miss

**The cache key is the photograph's digest, so `identify` computes it first and decodes only cache misses.** It used to run `geometry.detect_card` and `images.prepare` over every photograph before asking the store whether it already owned the answer, though the cache's own question is `Cache.reusable(key, photo_sha256)` and the decode was never an input to it. The order is hash, cache, refuse, prepare: every photograph is hashed, the store is asked, a card naming a game no registry entry answers is refused by name, and only what is left is cropped and downscaled. Hashing is 0.687 ms a photograph against about 115 ms for `detect_card` plus `prepare` (167 times), and hashing all 2,535 photographs (4.4 GB) takes 2.89 seconds, which makes a store-wide press affordable. The submitted set is unchanged.

- **`prepared is None` meant two things at once,** "this photograph could not be read" and "there are no bytes to send". Under hash-first a cache hit is never prepared either. A reorder that left the consumers alone would have counted 464 healthy cached cards as unreadable and written `photo_sha256: null` on their records, where `cli/resolve.realign` reads a missing digest as `blind` and D36's realign can no longer re-bind the card. `Item.stage` (`pending`, `cached`, `unreadable`, `refused`) separates them. It is not `Item.status`, which is on the wire and unchanged (a cache hit still records `succeeded`, an unreadable photograph `unreadable`, an unregistered game `unknown_game`). `Item.photo_sha256` belongs to the item, and is `None` only when the bytes could not be read at all, so a photograph that hashed and then failed to decode keeps its digest.
- **Two counters changed denominator, and the line says so.** The crop counters run over the send set, since a crop never made is not a crop, and the preflight reads `N cropped of the M being sent`. `cache hits` is counted, not subtracted: every `unknown_game` and `unwritten_prompt` card had been reported as a cache hit on the line an operator reads to decide whether to spend.
- **Hashing is its own step.** `images.prepare` called `sha256_of` outside its `try`, so an `OSError` was never an `ImageError` and one deleted file killed the command on the first photograph and said nothing of the other 677. It is a named failure now.
- **The proof is T7 `check_identify_preflight_stage`.** One directory holds one of each outcome, two presses run over it with the second paying nothing, and 19 assertions read the operator's own preflight lines. Reverting each consumer to its pre-reorder form turns seven of nine arms red. The arm that deletes the gate left every other assertion green, since hash-first and prepare-everything agree on every outcome and differ only in work done, so the check counts decodes: the second press decodes exactly one photograph, the non-image. Two arms are equivalent mutants, re-checked against the whole harness and reported as such.

It widens nothing: `identify` still takes one capture directory.
