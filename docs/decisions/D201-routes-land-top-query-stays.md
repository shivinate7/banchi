## D201 — Routes land at top; query changes stay

**The bug, found on the phone shell.** Nothing in `App.tsx` or `App.css` called `scrollTo` or set `scrollTop`. `.bn-shell-main` has no `overflow` rule, so the window is the one thing that scrolls at every width this shell is verified at (1440, 820, 390). No second scroller exists to reset. `.bn-view` remounts on every route change, keyed on `path`, but a DOM remount does not move the browser's own scroll position. Scrolling `#/capture` down and then leading to `#/runs` landed on the new screen already scrolled. So did tapping `#/inventory` from a scrolled screen. At the rig's 390-wide viewport, scrolling Capture to 300px and pressing `,I` landed Inventory at `scrollY: 247` rather than `0`. Inventory has 122 cards, reliably taller than the viewport. Runs, under the shared small fixture, draws no run at all, so its scroll clamp reads `0` whether or not anything reset it. That is why the first attempt at this guard passed for the wrong reason. It was re-pointed at a route tall enough to prove the fix.

**The fix is one hook beside the one already keyed on `path`.** `path` comes from `currentPath()`, which splits on `?` and drops everything after it. So a `useEffect` with `[path]` as its dependency fires on `#/capture` -> `#/runs`. It does NOT fire on `#/pricing` -> `#/pricing?band=top`. That second case is D277's own lens. `?band=top|bottom` filters the same screen, not a different one. Staleness there is something the operator dismisses, not something a navigation clears. A scroll reset keyed on the full hash (path + query) would re-break what D277 built: the click that opens the band view would land the operator at the top of a list they were already reading. Keying on the query-stripped `path` gets both halves. It reuses the array `App.tsx` already uses for the drawer, palette and keys-sheet dismissal effect two lines above.

**The window is what resets, and that is a fact about this tree.** A shell that gave its scroll region its own `overflow-y` would need the reset on that element instead of the window. This one does not. The guard's comment records the confirmation for the next screen that does grow a second scroller. It was made before writing the fix, rather than assuming a "shell main" div is always the scroller.

### Mechanized

`app/tests/phone.spec.ts`, `leaving a scrolled screen lands the next one at the top`. It scrolls `#/capture` to 300px. It finds `#/capture` off the drawer's own roster, never a typed hash. It confirms the scroll actually moved. It leads to Inventory with `,I`. It asserts the document is taller than the viewport plus the old scroll offset, so a short destination can never pass by the browser's own clamp. It asserts `window.scrollY === 0`. Red on the unfixed tree at `scrollY: 247`; green with the fix. Run through `make design-check`. `docs-audit`'s `route rosters` row refuses a third pinned literal in this file.

### Not mechanized

**Whether a future scroll region needs the same treatment.** If a screen ever gives `.bn-shell-main` (or any other ancestor of `.bn-view`) its own `overflow-y`, this fix's `window.scrollTo(0, 0)` stops being the right target. Nothing here would say so. The guard asserts `window.scrollY`, which would silently read `0` forever once the window itself stopped being the scroller. The comment beside the fix names this as the thing to check first.
