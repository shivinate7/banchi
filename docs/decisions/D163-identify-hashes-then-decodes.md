# D163 — Identify hashes first, decodes on a miss

**The cache key is the photograph's digest. So `identify` computes the digest first and decodes only cache misses.** It used to run `geometry.detect_card` and `images.prepare` over every photograph before it asked the store whether the answer was already known. The cache's own question is `Cache.reusable(key, photo_sha256)`. The decode was never an input to it. The order is now hash, cache, refuse, prepare. Every photograph is hashed, and the store is asked. A card that names a game with no registry entry is refused by name. Only the rest is cropped and downscaled. Hashing takes 0.687 ms a photograph, against about 115 ms for `detect_card` plus `prepare` (167 times as slow). Hashing all 2,535 photographs (4.4 GB) takes 2.89 seconds, so a store-wide press is affordable. The submitted set is unchanged.

- **`prepared is None` meant two things.** It meant "this photograph could not be read" and "there are no bytes to send". Under hash-first, a cache hit is never prepared either. A reorder that left the consumers alone would have counted 464 healthy cached cards as unreadable. It would also have written `photo_sha256: null` on their records. There, `cli/resolve.realign` reads a missing digest as `blind`, and D36's realign can no longer re-bind the card. `Item.stage` (`pending`, `cached`, `unreadable`, `refused`) separates the two cases. It is not `Item.status`. `Item.status` is on the wire and unchanged. A cache hit still records `succeeded`. An unreadable photograph records `unreadable`. An unregistered game records `unknown_game`. `Item.photo_sha256` belongs to the item. It is `None` only when the bytes could not be read at all. A photograph that hashed and then failed to decode keeps its digest.
- **Two counters changed denominator, and the output says so.** The crop counters run over the send set, because a crop never made is not a crop. The preflight reads `N cropped of the M being sent`. `cache hits` is counted, not subtracted. Every `unknown_game` and `unwritten_prompt` card had been reported as a cache hit. Operators read that line to decide whether to spend.
- **Hashing is its own step.** `images.prepare` called `sha256_of` outside its `try`. So an `OSError` was never an `ImageError`. One deleted file stopped the command on the first photograph and said nothing about the other 677. It is now a named failure.
- **The proof is T7 `check_identify_preflight_stage`.** One directory holds one photograph of each outcome. Two presses run over it, and the second pays nothing. 19 assertions read the operator's own preflight lines. Reverting each consumer to its old form turns seven of nine arms red. The arm that deletes the gate left every other assertion green. Hash-first and prepare-everything agree on every outcome. They differ only in the work done. So the check counts decodes. The second press decodes exactly one photograph, the non-image. Two arms are equivalent mutants. They were re-checked against the whole harness and reported as such.

It widens nothing. `identify` still takes one capture directory.
