# Pricing (`#/pricing`)

**Coverage:** 1440px and 1280px, light and dark theme (via `document.documentElement.setAttribute('data-theme', …)`, verified against live computed styles). States seen: populated worklist (9 runs / 843 SKUs, "Above the cut-off" section), the two-panel landing deck, the preset/custom rule strip, the ship bar. Measurements taken with `getComputedStyle` / `getBoundingClientRect` against the owner's real store at `localhost:8000`, not screenshots (the Browser pane could not composite frames in this session — see "What I could not check").

## Findings

### 1. The landing deck's two panels end at different heights with no shared floor
**What I saw:** "The cut-off" panel and "Ready to write" panel sit side by side in a two-column grid. Measured at 1440, both dark and light theme: left panel `height: 225px`, bottom edge at `y=407`; right panel `height: 339px`, bottom edge at `y=521`. A 114px gap between the two bottom edges, with the shorter panel's card simply stopping short and the row beneath (the preset/custom rule strip) starting under the taller one.
**Where:** `app/src/Pricing.css:307-320` (`.pricing-deck { grid-template-columns: minmax(0, 1fr); gap: var(--bn-4); align-items: start; }`). The file's own comment at lines 311-314 says this was chosen deliberately over stretching the panels to a common height, because stretching opened a 136px hollow band that "read as content that failed to load."
**Severity:** medium. The team already tried and rejected the "stretch" fix, but landed on the other extreme: two bordered, shadowed `.bn-panel` cards in one row with a 114px jagged step between their bottom edges reads just as much like something broke, especially since both panels share the same background and elevation and sit on the same baseline at the top. Neither of the two states considered (full stretch vs. free height) addresses the actual problem, which is that a shadowed card is a strong visual unit and two of different heights side by side always look unresolved.
**Fix:** give the shorter panel a matching visual floor instead of matching height — e.g., align both panels' internal content top-down and let the shorter one show a `bn-hairline`-separated footer strip the same colour as its background, or drop the "Ready to write" panel's own bottom padding so its natural height is closer to the left panel's, or put the two cards on a shared row background so a height difference reads as "this one has less to say" instead of "the layout broke."
**Recurs elsewhere in slice:** No — `#/revenue`, `#/product` and `#/codes` do not use `.pricing-deck`.

### 2. `.pricing-locked` uses two CSS custom properties that are never defined
**What I saw:** `.pricing-locked` (the "sold out at TCGplayer, nothing to price" pill) is written as `background: var(--bn-well); color: var(--bn-muted);`. Neither `--bn-well` nor `--bn-muted` exists anywhere in `tokens.css`, `kit.css`, or any other stylesheet in the repo (confirmed by `grep -rn` across `app/src`). Live-tested in the running app: a probe element styled with `background: var(--bn-well); color: var(--bn-muted);` computed to `background-color: rgba(0,0,0,0)` (fully transparent — the `background` shorthand is invalidated wholesale by the bad reference) and `color: rgb(238,240,244)` in dark theme / `rgb(15,18,23)` in light theme — i.e. the *full-strength* ink colour, not a muted one, because an unresolvable `var()` falls back to the property's inherited value.
**Where:** `app/src/Pricing.css:835-836` (inside `.pricing-locked`, lines 827-842).
**Severity:** high. The comment directly above this rule says the intent is "Muted rather than warned: nothing is wrong, there is simply nothing to do here." As written, the pill renders with no background at all and full-contrast text — the opposite of muted — every time a row has no live listing to price. This silently defeats the one visual cue the design relies on to tell an operator "skip this row."
**Fix:** use real tokens — almost certainly `var(--bn-surface-2)` for the well background (matching the neighbouring `.pricing-held` treatment's intent) and `var(--bn-ink-3)` for the muted text, matching every other "muted" use in this same file.
**Recurs elsewhere in slice:** yes, the same undefined-token pattern (a different property, same root cause) appears in `#/product` — see `product.md` finding on `--bn-border`.

### 3. Segmented custom-rule row sits 14px below the preset row with no declared rhythm
**What I saw:** the preset segmented control (`Match market / Market −5% / TCG Low −1% / Custom`) sits at `y=537`, height 34px (bottom at 571). The custom-rule segmented row (`Undercut / Markup … Market / TCG Low`) starts at `y=579` — an 8px gap, which **is** `--bn-2` and therefore consistent with the spacing scale. No defect here on inspection — noting it because it looked suspicious in a first screenshot pass and needed a second, more careful measurement to clear it. Recorded so a later reviewer does not re-spend time on it.
**Severity:** n/a (cleared).

### 4. Money and quantity figures in the worklist are formatted as raw server strings, not through the shared `money()`/`moneyGrouped()` helpers
**What I saw:** `Pricing.tsx` builds every price string itself — e.g. `` `$${sku.snap[column.field]}` `` (line 3531) — rather than importing `money`/`moneyGrouped` from `./money.ts`, which every other money-bearing screen in this slice (`Revenue.tsx`, `ProductHistory.tsx`) uses. On screen this currently reads fine (`$0.29`, `$13.44`, …, all two decimals) because the server always sends two-decimal strings, so there is no visible defect today.
**Where:** `app/src/Pricing.tsx:3531` and surrounding column-rendering code (search `sku.snap[column.field]`).
**Severity:** nit. This is a latent inconsistency rather than an observed bug: the one file in this slice with the densest, highest-stakes money display (a hundred real pricing decisions in a sitting) is the one file that does not go through the shared formatter that the rest of the app relies on for "a dollar amount, said the same way everywhere." If the server ever emits a value with more or fewer than two decimal places, or a bare integer, this screen would render it differently from every other screen without anyone deciding that.
**Fix:** route these cells through `money()` for defence in depth, or add a comment explaining why this screen is deliberately exempt (e.g., because the value must round-trip byte-for-byte back into the field for editing).
**Recurs elsewhere in slice:** no.

### 5. `Holding N` pill and hold-reason picker use `bn-pill`-style geometry inconsistently with `bn-chip`
**What I saw:** the "Holding 19" control in the toolbar renders as a `bn-chip`-styled pill (`border-radius: 999px`, height 28px) sitting beside plain rectangular 6px-radius buttons ("Load trends," "Runs") in the same row, at the same height. This is an intentional pill-vs-button distinction elsewhere in the kit (status pills are round, actions are square-radius), so on reflection this is consistent with the design system rather than a defect — recorded as cleared after measurement (radius 999px vs 6px, by design, per `kit.css:239` `.bn-btn-pill`).
**Severity:** n/a (cleared).
