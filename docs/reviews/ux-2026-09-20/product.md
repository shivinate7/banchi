# Product history (`#/product`)

**Coverage:** 1440px and 1280px, light and dark theme. States seen: the "unknown SKU" refusal (`?sku=8677865`, a SKU with real order history but no card in this store) and a fully populated product page (`?sku=8937645`, "Lillie's Determination · ME01: Mega Evolution · Near Mint", four range panels: Weekly/annual, Daily/month, 3-day/quarter, Weekly/semiannual). Reached by deep link with a real SKU pulled live from `GET /pipeline/pricing` and `GET /orders`, per the brief (this screen carries no in-app link — confirmed by `grep -rn "#/product"` across `app/src`, which finds only the file's own hash definition). Measurements via `getComputedStyle`/`getBoundingClientRect` (screenshots unavailable this session).

## Findings

### 1. The range-panel border is invisible in both themes because of an undefined custom property
**What I saw:** `.producthistory-range` (the container for each of the four bucket-width charts) is written as `border: 1px solid var(--bn-border);`. `--bn-border` is never defined anywhere in the repo (`tokens.css`, `kit.css`, no screen sheet — confirmed by `grep -rn -- "--bn-border:"` across `app/src`). Because `border` is a CSS shorthand, an unresolvable `var()` inside it invalidates the *whole* shorthand at computed-value time, not just the colour: live-measured on the actual element, `border-top-width: 0px` and `border-top-style: none`. There is also no `box-shadow` on this class. In light theme the panel's own background (`rgb(255,255,255)`) sits on the page background (`rgb(244,245,248)`) with nothing else to mark its edge — a roughly 4 L* difference, confirmed live.
**Where:** `app/src/ProductHistory.css:69-77` (`.producthistory-range`).
**Severity:** high. All four bucket panels on this screen's whole reason for existing (comparing price history at different granularities) currently render with **no visible boundary at all** in light theme — they are two shades of near-white floating on the page with no line, no shadow, and no other panel treatment to tell them apart from the page background. In dark theme the effect is softer (surface `#14171c` on page `#0c0e12` gives more contrast) but the intended hairline is still completely absent — confirmed live: `border-top-style: "none"`.
**Fix:** define `--bn-border` (most likely meant to be `var(--bn-line)`, matching every other hairline in this kit) or change the rule to reference an existing token directly.
**Recurs elsewhere in slice:** yes — the same undefined-custom-property pattern (different tokens, same root cause) appears in `#/pricing`'s `.pricing-locked` (`--bn-well`, `--bn-muted`), see `pricing.md` finding 2. Three separate undefined tokens across two files in this slice suggests this is worth a repo-wide sweep (`grep -oE 'var\(--[a-zA-Z0-9-]+' app/src/*.css` against the tokens actually defined in `tokens.css`) rather than three one-off fixes.

### 2. A range panel's human label and its machine-readable range key overlap onto two lines instead of sitting side by side
**What I saw:** each panel's header is built as `<div><h3>{label}</h3><span className="producthistory-machine">{range.range}</span></div>` — e.g. `<h3>Weekly</h3><span class="producthistory-machine">annual</span>`. The CSS gives the mono-font `.producthistory-machine` span `margin-left: var(--bn-2)` (8px), which reads as "sits 8px to the right of the label." Live-measured at 1440 and 1280 dark theme, the two elements do **not** sit on the same line: `h3` occupies `y: 416–434`; `.producthistory-machine` occupies `y: 439–453` — 5px *below* it, not beside it. This happens because the wrapping `<div>` has no styling of its own and is a flex child of `.producthistory-range-head` (`display:flex; justify-content:space-between`) with no `flex-grow`; a bare block-level `<div>` in a flex row shrinks to fit its content's own max line width. Since `<h3>` is a block element, it forces its own line, and the div's shrink-to-fit width ends up equal to the `<h3>`'s own text width (measured: 54.52px, exactly matching "Weekly"'s rendered width) — leaving no room on that line for the sibling span, which wraps underneath instead of sitting beside it as the 8px `margin-left` implies it should.
**Where:** `app/src/ProductHistory.tsx:205-210` (the `<div><h3>…</h3><span className="producthistory-machine">…</span></div>` markup) and `app/src/ProductHistory.css:78-97` (`.producthistory-range-head`, `.producthistory-range-head h3`, `.producthistory-machine`).
**Severity:** medium. On every one of the four panels, the bold display-face label and its muted mono "which range key is this" caption stack into two cramped, near-touching lines (5px apart, no visual grouping) instead of reading as one clean "Weekly · annual"-style header. It reproduces identically at both 1440 and 1280 (not a narrow-width wrap — the wrapping div is simply too narrow at any width because it never grows).
**Fix:** give the wrapping `<div>` `display: flex; align-items: baseline; gap: var(--bn-2)` (matching the parent header's own flex pattern one level up) instead of leaving it an unstyled block, or drop the wrapper and let `.producthistory-range-head` place the `h3` and the span as two direct flex children.

### 3. `Icon name="dot"` used for the legend's "your sale" marker draws a filled circle rotated 45°, not a diamond glyph
**What I saw:** `Legend()`'s second entry is `<Icon name="dot" size={10} className="producthistory-legend-diamond" />`, and `.producthistory-legend-diamond { transform: rotate(45deg); }` rotates it to read as a diamond next to the chart's own diamond-shaped sale markers (`diamond()` helper, `ProductHistory.tsx:197-199`, used by the chart itself). A circular dot icon rotated 45° is visually indistinguishable from an unrotated circular dot — rotating a circle does nothing. I did not have a rendering of the actual `dot` icon's SVG path to confirm it is perfectly circular (icons can be asymmetric), so this is reported as a likely-but-unconfirmed mismatch between the legend swatch and the chart's own diamond marker shape, rather than a certainty.
**Where:** `app/src/ProductHistory.tsx:232` (`<Icon name="dot" … className="producthistory-legend-diamond" />`), `app/src/ProductHistory.css:67` (`.producthistory-legend-diamond { color: var(--bn-accent); transform: rotate(45deg); }`), chart marker shape at `app/src/ProductHistory.tsx:197-199`.
**Severity:** nit (unconfirmed). If `Icon name="dot"` is a plain circle, the `rotate(45deg)` is dead code and the legend swatch does not match the chart's own diamond mark shape, which is exactly the kind of "legend vs. actual chart mark" mismatch the brief calls out. If `dot`'s SVG path is not circular, this may be fine.
**Fix (if confirmed):** use a diamond-shaped icon (or an inline SVG matching the chart's own `diamond()` path) for the legend swatch instead of a rotated circle.
