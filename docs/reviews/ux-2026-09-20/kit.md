# Gallery / kit sheet (`#/gallery`) — UX review

## Coverage
- Width: 1440x900 primarily (the Browser pane was hidden for most of this pass — see "What I could not check"); reached via direct hash navigation (`#/gallery`), not the command palette, since the route is a registered route regardless of entry point.
- Theme: light (default, confirmed via `location` state); dark not visually re-verified for this screen specifically beyond the CSS rules already read (the sheet claims to show both treatments on one page for the mark — see finding 6).
- Method: full `get_page_text` scrape of the rendered sheet (all sections, "Foundations" through "Card locations"), cross-checked against `app/src/Gallery.tsx` structure (via `make orient`), `app/src/kit.css`, and live CSSOM queries (`document.querySelectorAll`, `getComputedStyle`) for specific primitives. Screenshots were available only briefly at the start of the session.
- Sections reached (all, per the sheet's own nav): Color, Type, Space & radius, Elevation, Motion, Icons, Buttons, Keycaps, Pills & dots, Fields, Segmented & tabs, Notice, Receipt & toast, Empty state, Skeleton & progress, Data, Surfaces & menu, Pull-confirm, Position bar, Position label, Search field, Card locations, The mark.

## Findings

1. **The sheet's own documented type scale (12 named sizes, `2xs`=10px to `5xl`=48px) does not cover the sizes the product's largest single-purpose screen actually ships.** Fulfillment.css alone uses 24px, 26px, 32px, 34px, 38px and 56px as literal `font-size` values — none of which is one of the 12 named tokens, and 56px exceeds even `5xl` (48px, documented in the sheet as "Home greeting," its largest use). The Kit sheet presents the type scale as exhaustive ("Every primitive the screens are built from, drawn from the tokens") but a whole screen's type is invisible on it.
   Where: gallery text confirms the 12-size scale; `app/src/Fulfillment.css` lines 126 (38px), 190 (56px), 199-206 (28px), 596-602 (26px via `.ff-row-name`), 610-620 (32px/36px `.fulfillment-place`), 654-661 (34px `.ff-card-name`) are the off-scale sizes.
   Severity: high. This is exactly the kind of gap the brief asks to be found: "are there obvious gaps a product this size would need" — a kit that omits an entire screen's type register is not describing the system, it's describing a subset of it.
   Fix: either add a documented "Fulfiller" or "arm's-length" type sub-scale to the Kit's Type section (since these sizes are clearly deliberate, not accidental — Fulfillment.css's own comments argue for readability at distance), or fold the actual values Fulfillment uses back onto the nearest scale step so there is one scale, not two.
   Recurs: n/a — this is specifically the sheet failing to represent Fulfillment; see `system.md` for the full raw-px inventory.

2. **`.review-key` (the review queue's row keycap, 28px) is called out in the sheet's own copy as "a candidate for promotion"** — i.e., the sheet documents a known duplicate/orphaned primitive and ships it anyway rather than either promoting it into `.bn-kbd`'s family or removing the call-out.
   Where: gallery "Keycaps" section text: "ROW KEYCAP · 28PX ... The review queue's row keycap — `.review-key`, a candidate for promotion."
   Severity: medium. A design system document that flags its own debt without resolving it is honest, but it means the "two components doing one job" question the brief asks has an admitted, unresolved answer sitting in the deliverable itself.
   Fix: promote `.review-key` into a `.bn-kbd-lg`/`.bn-kbd-row` variant now that its shape is understood well enough to be exhibited, or explain in the sheet why it must stay separate.
   Recurs: this is the only primitive on the sheet that self-flags this way; other likely duplicates (see `system.md`, e.g. `.ff-empty-art` vs `.bn-empty-art`) are not called out at all, which is a gap in the sheet's own self-audit — it caught one instance of the pattern and missed others.

3. **`font-weight: 650`, used in four sheets outside the kit (`LiveReconcile.css`, `Markdown.css`, `RunPanel.css`, `Orders.css`) and referenced from `fonts.css`'s own header comment, is not achievable with the shipped fonts and silently renders as 700** — the exact same visual weight as the product's ordinary bold. `fonts.css`'s own comment states this directly: "resolves against these discrete faces to 700." The Kit sheet's Type section does not show a weight scale at all (only sizes), so this dead value has no page where a reviewer would ever see that "650" and "700" are visually identical in this product.
   Where: `app/src/fonts.css` lines 24-28 (the comment stating the fact), `app/src/LiveReconcile.css:89`, `app/src/Markdown.css:97`, `app/src/RunPanel.css:493`, `app/src/ClearPrices.css:90`, `app/src/Orders.css:1186`.
   Severity: medium. It's not a visible defect (700 is a perfectly good weight), but it's six rules across six files that read as "we chose a deliberately intermediate weight here" when in fact they chose ordinary bold with extra characters — a false signal to the next person reading the CSS, and a hole in the kit's documentation of what weight values actually mean anything in this product.
   Fix: either self-host a variable-weight build of Inter/Manrope so `650` is real, or replace all six occurrences with `700` and delete the claim that 650 is a distinct choice.
   Recurs: counted above (6 occurrences across 6 files) — this is a system-level finding, cross-referenced in `system.md`.

4. **The mark specimens below 64px are explicitly described in the sheet as decorative-only ("specimens here rather than call sites") for six of seven size steps (16/26/30/32/40/44px), with only two real call sites in the whole product (40px on crash pages, 44px on the Fulfiller's header).** This means five of the seven sizes shown as a "range" on the flagship brand asset's own page are not used anywhere a person will ever see them at runtime.
   Where: gallery "The mark" → "Across its size range" section text.
   Severity: nit. It's honestly labeled as specimens, so this isn't a hidden problem, but a design-system page presenting five unused sizes beside two real ones, with no visual distinction between "shown for the range" and "actually shipped," makes the sheet harder to read as an inventory of what's live versus what's exploratory.
   Fix: visually separate "shipped" sizes from "specimen" sizes in this row (e.g., a small "not used" tag on the five specimen-only tiles), matching the care already taken to write the distinction in prose.
   Recurs: n/a.

5. **The Pull-confirm section documents three states (default, pressed, disabled) and explicitly notes "Never appears in the Fulfillment view; that view has no disabled state" for the disabled swatch** — yet Fulfillment's own action button (`.ff-step`, see `fulfillment.md` finding 2) is a completely different component from the kit's `.pull-confirm` shown here, despite the sheet's own framing ("The one solid fill the Fulfiller ever sees") implying `.pull-confirm` IS what the Fulfiller sees. In the live Fulfillment screen, the first-step button before a search result resolves is `.ff-step` (outline style), and only the confirmed pull step (`.ff .pull-confirm`, `width:100%`) uses the real kit component. The sheet's caption overstates how much of the Fulfiller's screen is actually built from this one primitive.
   Where: gallery "Pull-confirm" section text ("The one solid fill the Fulfiller ever sees"); `app/src/Fulfillment.css:801` (`.ff .pull-confirm { width: 100%; }`, the real integration point) versus `:841-860` (`.ff-step`, a separate hand-rolled button that precedes it in the same flow).
   Severity: nit. Not wrong, exactly — the pull-confirm probably is the only solid FILL — but a reader of the kit page would reasonably conclude the Fulfiller's action flow is one component, when it is two different button implementations in sequence (quiet outline, then solid pull-confirm).
   Recurs: relates to finding 2 in `fulfillment.md`.

6. **The mark's dark-ground treatment is explained via a long code comment (in `kit.css`, quoted verbatim in the sheet's rendered text) about a system-preference/stored-theme mismatch bug that was "shipped and measured"** — i.e., the sheet's live prose is effectively a bug-report artifact left in production copy ("bracket url('#_r_0_m') — bluesteel's #FFFFFF-to-#8FA4B8 chrome drawn as a frame around near-black type on a light sidebar"). This is technical incident narration, not design documentation, sitting in a screen meant to teach the system to a person.
   Where: `app/src/kit.css:1039-1072`, rendered into the "The mark" → "On the dark ground" section of `#/gallery`.
   Severity: nit. It doesn't break anything, but a design-system reference page carrying "THAT WAS SHIPPED AND MEASURED" postmortem language, rather than a plain statement of the current rule, works against the sheet's own stated purpose of teaching the system at a glance.
   Fix: keep the postmortem in a code comment; give the on-page copy a single plain sentence ("the bracket always matches the app's own theme, never the OS theme, so both can be shown side by side here").
   Recurs: n/a — unique to this one section, but worth checking the other prose blocks on this sheet for similar leakage (not exhaustively checked here).

7. **Icons section lists 70 names with no visual grid captured in this pass** (text-only scrape) — I could not verify stroke-width consistency (documented as 1.75), optical sizing, or baseline alignment across the 70 icons visually. This is a coverage gap, not a finding — see "What I could not check."
